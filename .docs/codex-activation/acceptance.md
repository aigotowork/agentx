# Shared runtime acceptance

This report owns the verification projection of [R1–R9 and A1–A11](./README.md#需求与边界), not a second requirements source. `lobo` authored and executed the original independent cases, fixtures and serialized shared checks/builds; those assignments are closed. `zomi` owns the subsequent dependency follow-ups recorded below. Original feature corrections remain attributed to their domain owners; authored coverage and observed support remain distinct below.

## Verification model

The subject is the real AgentX composition: launcher → shared Codex service connection → bidirectional bridge → thread attachment → pending-mail claim → native input record → fenced cursor commit. Independent effect checks use native history, SQLite cursor/claim state, a second surviving connection and fixture-owned shell output. A response observed on the same mock that generated it cannot prove these effects.

| Evidence layer | Valid claim | Limit |
| --- | --- | --- |
| Production-contract tests with adversarial values/events | Routing, arbitration, storage fences and recovery rules for the tested transitions | Does not prove a native protocol, daemon or launcher works |
| AgentX process plus scripted native protocol fixture | Actual CLI composition, frame routing, failure injection and cleanup | Scripted native behavior cannot establish native compatibility |
| Real native Codex plus fixed loopback Responses fixture | Actual native connections, hooks, input records, tool environment, lifecycle and AgentX composition | No paid inference, remote provider, arbitrary model behavior or unmodified product UI coverage |
| Unmodified outer product client API | Actual installed provider receives/handles autonomous work and controls | Must name version, environment and real steps; generic native client results cannot stand in for Paseo. Desktop/mobile GUI rendering is outside this backend acceptance unless explicitly exercised. |

Run only cases whose production paths are usable. Keep failed/unknown cases visible, retain their first trace, and rerun a passed case only after a relevant change. Full acceptance requires the real composition and the A1/A10 unmodified outer client boundary clarified by controller request #1052: installed Paseo provider API is sufficient; live desktop/mobile GUI rendering is not an added requirement.

## Derived cases

Each row states the distinguishing state/event and independent oracle. Case IDs are stable test/evidence references. Related source requirements remain in the canonical [acceptance table](./README.md#场景与验收).

| Case | Starting state and event | Required observation and failure/recovery oracle |
| --- | --- | --- |
| A1.1 idle round trip | Parent root sends a child assignment, completes its user turn; child replies after parent idle with outer stdin left open and no new request | Actual AgentX send/receive records identify parent and child; same native parent thread records exactly one matching batch and continues; parent produces a business reply. A tool result alone is insufficient. |
| A1.2 duplicate notification | Same pending batch produces repeated wake signals before/after input write | One active claim and one real batch input; late mail beyond the frozen last ID remains pending. |
| A2.1 active steer | A fixed loopback gate holds an active native turn; pending mail arrives | `turn/steer` uses the observed active turn ID and real batch text; the original turn survives; matching completed userMessage commits only that batch. |
| A2.2 waiting controls | Native thread is awaiting approval or user answer while mail arrives | No internal start/steer; approval/answer and cancel still reach native; queue and cursor stay pending until state is eligible. |
| A2.3 stale expected turn | Turn completes between observation and steer | Known expected-ID rejection refreshes state before a new eligible attempt; unknown native errors do not release/replay an issued batch. |
| A3.1 user first | User input or interrupt is queued before an unissued internal batch | Preserve user request method/ID/body and response; re-evaluate mail admission without taking over the user request. |
| A3.2 internal first | Internal write crosses issue boundary, then user input arrives; userMessage record precedes internal response in one ordering | Both real user inputs remain visible, one cursor commit, no synthetic success and no internal RPC response at outer stdout. |
| A3.3 cancel/archive race | Cancel or close succeeds immediately before/after child reply | Retired attachment never receives automatic input; pending/unknown mail is retained without silently reopening a thread. |
| A4.1 two roots | One backend, two outer root starts with distinct environment/identity; responses return out of order | Distinct participants and bindings match their own request results; shell A→B→A reports the correct per-thread identity each time; hook payload session ID resolves the same identity despite shared daemon environment. |
| A4.2 resume/fork | Resume same root twice, fork once, close one attachment | Resume retains canonical participant without duplicate active owner; fork gets a distinct participant; original mailbox/bootstrap remain unchanged. Conflicting active ownership is explicit. |
| A4.3 malformed lifecycle result | Failed root request, unrelated started event, or lost creation response | No guessed binding or process-wide default recipient; unknown state does not deliver. |
| A5.1 internal threads | Native subagent/memory/ephemeral events and thread/read/list interleave with a bound parent | No participant creation/rebinding from events or read-only requests; parent attachment/cursor unchanged. Explicit outer ephemeral creation remains eligible. |
| A6.1 request IDs | Concurrent client and internal requests use integer `1`, string `"1"`, int64 limits, Unicode and a string resembling an internal ID | Unique downstream IDs; exact original ID type/value restored, internal response consumed internally, opaque nested IDs/unknown fields preserved. |
| A6.2 server direction | Native approval, user-input, dynamic-tool and unknown requests reuse a client request ID, followed by serverRequest/resolved and late response | Independent direction ledger; native ID and embedded requestId unchanged; external replies routed to native; resolved outstanding control is cleared without affecting client request. |
| A6.3 framing/subscription | Unknown method/notification with >256 KiB UTF-8 content; outer opt-out removes an event required internally | Complete JSON frames in order, no stdout diagnostics; internal observation remains usable and outer filtering respects its original opt-out. |
| A7.1 blocked input | Hook rejects real batch while start succeeds and turn completes with no userMessage | Cursor does not move; blocked batch retains reason and does not trigger an unlimited empty-turn loop. |
| A7.2 receipt mismatch | UserMessage has wrong home/thread/clientId/content, partial batch content, or only item/started | No delivery commit; exact completed record with frozen content can commit. RPC success and turn/completed alone never commit. |
| A8.1 lost response | Native input write followed by EOF or missing response/record | Issued claim persists as uncertain; timeout/lease expiry/new execution cannot justify replay. Reliable matching history can resolve delivered. |
| A8.2 rebind/stale receipt | Participant row is recreated or binding/execution changes before an old matching receipt arrives | Old receipt cannot advance new cursor or select new thread; unresolved old batch blocks duplicate lineage input until explicit fenced reconciliation. |
| A8.3 negative recovery | History read fails/is paginated/incomplete, then complete authoritative absence with old execution unable to act | Incomplete absence stays uncertain; only the latter proof permits retry. Restarted store preserves the distinction. |
| A8.4 consumer race | Native driver, Codex hook and explicit listen concurrently try the same mailbox | Shared transaction admits at most one claim; losing readers emit no duplicated context and do not move cursor. Native-input hooks retain identity/status without consuming that batch. |
| A9.1 concurrent reuse | Two simultaneous production entries use same isolated compatible home/config/native executable | Both connect to one real backend generation/PID; no per-entry backend fallback. Different incompatible configuration reports conflict without replacing the service. |
| A9.2 proxy EOF/signal | Close A stdin or signal only A while B remains connected | A-owned driver stops; B performs another real request/turn on the same backend generation; no daemon stop or thread close synthesized. All fixture resources later cleaned by their owner. |
| A9.3 version/environment | Native `--version`, project `.envrc`, relative home, deleted variables, binary body on non-app-server stdio | Version stdout exact with no participant/service setup; effective environment chosen before service scope; failed environment setup creates no state; existing opaque stdio path remains byte exact. |
| A9.4 capability conflict | Pre-connection service version/transport is unsupported, or a compatible connection loses an observation prerequisite | Unsupported acquisition explicitly rejects without daemon mutation or private fallback. After a compatible connection exists, usable native traffic continues while autonomous delivery is disabled/reported. No guessed inputs or old-version support claim. |
| A10.1 autonomous visibility | Outer client waits without new user input when mail triggers a real turn | Real userMessage, turn and output events appear in native order; internal RPC responses never leak; controls remain responsive. Generic client and actual unmodified Paseo receive separate dispositions. |
| A11.1 no Codex dependency | Remove/poison Codex executable inside fixture, run affected non-Codex launch modes | Claude print and existing PTY/hook/plugin flows launch without a Codex service/preflight. Existing status, identity, stdin/stdout and cleanup semantics remain. |
| A11.2 heterogeneous routing | Native Codex parent exchanges mail with a non-Codex AgentX participant, and reverse direction | Real routing and delivery evidence names both provider identities and correct recipient; shared cursor/hook changes do not steal the other's mail. |
| A11.3 retained delivery | Affected PTY drafts, busy/approval gates, hook flush failures and plugin paths | Existing user drafts and gates protected; successful flush commits only the intended recipient generation; failures preserve pending mail; scoped provider regression results retained. |

The combinations above are chosen where authority, effects or target identity can change. We do not enumerate unrelated model output, every upstream method or every OS. Unknown native methods must still survive the envelope path. Windows/macOS/Android, paid providers and arbitrary outer UI behavior need explicit evidence before any support claim.

## Codex 0.170.0 terminal sharing diagnosis

An isolated Linux experiment used the installed native Codex 0.170.0 package, tmux 3.6a, one disposable `CODEX_HOME`, one native daemon, and a fixed loopback model. The control connection queried `thread/loaded/list` while each TUI was still running. Every case reached the model and wrote history in the same home.

| Terminal | Native TUI arguments added | Thread loaded on the shared daemon |
| --- | --- | --- |
| Direct PTY | None | Yes |
| Detached tmux | None | Yes |
| Direct PTY | `-c hooks.UserPromptSubmit=[]` | No |
| Detached tmux | `-c hooks.UserPromptSubmit=[]` | No |
| Detached tmux | `--remote unix://` and the same empty override | Yes |

The empty override declares no hook command: the difference is [Codex's automatic daemon-selection policy](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/daemon_startup.rs#L62-L125), not hook execution or terminal hosting. The explicit-remote row demonstrates connection only. The [native TUI's request projection](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/app_server_session.rs#L2450-L2533) does not forward `hooks` from CLI overrides as `thread/start.config`. Appending `--remote` alone therefore cannot preserve AgentX's per-session hooks.

The existing [shared stdio configuration composition](../../src/integrations/codex/configuration.rs#L205-L225) shows that the server can accept trusted hooks per thread. Ordinary terminal launches still use their existing path. The experiment made no launcher changes, stopped only the disposable daemon, and removed the fixture directories.

### Native TUI thread composition probe

The [disposable probe](./.tools/probe_terminal_attach.py) uses stock Linux Codex 0.170.0, tmux 3.6a, a fixed loopback model and a fixture hook. The direct tests connect both TUIs to the native daemon's own Unix socket. The separate historical comparison uses a private fixture adapter. The probe checks the exact thread ID, hook payload, tool environment, idle state, loaded-list membership and daemon PID record.

| Route | Observed result |
| --- | --- |
| `thread/start`, then direct TUI resume of the untouched blank thread | Native TUI rejects resume with `no rollout found for thread id`. |
| `thread/start`, set a legitimate title with `thread/name/set`, close setup before opening TUI | Earlier probe run: blank resume works, but both the fixture hook and tool identity are lost. |
| Start and name the blank thread, attach the TUI directly, then close setup | The blank thread appears in a second native Command Center with zero model requests. The first user prompt after setup closes uses the expected hook and tool identity. Selecting that thread through the second TUI and submitting another prompt preserves both identities and the native daemon generation. |
| Enter `/new` from the switched TUI | Stock TUI creates a distinct native thread without the fixture's hook or identity settings. This does not yet preserve the existing AgentX terminal integration across `/new`. |
| Independent native client sends fixture input to thread A while the switched TUI shows thread B | `turn/start` with A's thread ID and a client correlation ID records exactly one matching input on A. A runs with its original hook and tool identity, and B's recorded items stay unchanged. The independent connection carries its own request only; both TUIs remain connected directly. |
| Historical comparison: TUI through a fixture WebSocket adapter | The adapter adds per-thread configuration; the first supplied prompt uses the expected hook and tool identity. This does not qualify as an ordinary terminal launch. |

To repeat on Linux, run `python3 -B .docs/codex-activation/.tools/probe_terminal_attach.py --package /path/to/native/vendor/package --scratch-parent /dev/shm` from the checkout with bubblewrap, tmux, Node and the checkout's `ws` package available. The probe owns and cleans up its daemon, tmux server and temporary state. The direct case verifies native switching, fixture identity and routing traceable input to an idle thread independently of the TUI. It does not exercise AgentX participant ownership, actual mailbox delivery or cursor confirmation, concurrent user input, `agentx attach`, or upgrade of existing sessions. The [terminal-sharing Task](../../.controller/codex-terminal-sharing.task.md) owns the production design and remaining cases.

### Ordinary headless during AgentX daemon outage

`terminal-daemon-outage` in [the isolated native runner](../../tests/codex_shared_runtime.py) used the same fixed [AgentX 0.7.31 candidate archive](../../.artifacts/codex-terminal-sharing/candidate/agentx.zst) and real Linux Codex 0.170.0.
