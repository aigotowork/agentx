# 如果要做试验，怎样判断走得通

先选定相同的公开 URL、原生候选版本、导出的两份 OpenAPI、测试 scope、客户端版本和负载。现有 harness 会自建 loopback fixture；可复用下表的场景和断言，远端目标需另接测试入口。每条路线只需先做一个能否定其核心假设的小试验。[既有测试入口](../../tests/cloud_scope/README.md)

| 场景 | 扰动与观察 | 通过条件 |
| --- | --- | --- |
| 原消费者接入 | 两台宿主各启动一个 Agent，CLI 发信，真实 Provider 回复，管理端查看；记录请求 ID、消息 ID、精确实例与两端结果 | 两次 operation 均 confirmed，reply_to 指向原消息；管理页面正确显示 scope 和主机；相邻 scope 看不到本次消息 |
| 写成功、应答丢失 | 发信已提交时切断响应，随后重用原 ID；再改正文重用同一 ID；让同名目标换代 | 原请求返回原消息、原收件实例；改正文返回冲突，后继实例收不到旧信 |
| 领取后失联 | 领取后、确认前更换连接或服务实例；分别模拟 Provider 已接收和证据不明 | 原 claim 可恢复；有证据才确认；证据不明时保留待定，不能盲目重投 |
| 并发轮换与等待 | 一个旧 token 在等信，两位管理员带同一预期版本轮换；断线后重放胜方原请求 | 仅一次版本增长；旧 token 的新请求和旧等待失效；用新 token 能查原消息及回执，generation 不变 |
| 创建与恢复 | 在初始化与发布 scope 之间中断，按原请求重试；恢复后读邻居 scope 和管理概况 | 只出现一个可用 scope 和稳定 generation；重复请求拿回原回执；故意令一个 scope 不可读时统计能标出缺失 |
| 原生控制扩展 | 待该工作线有可测候选，测试零 Agent 主机、精确 launch / stop、领取前后租约失效、执行后上报丢失 | 实际进程与可观测回执相符；旧租约及错误实例不能执行；不确定的效果不会被执行第二次。[控制状态](../../.controller/cloud-daemon/wire.md) |

**三条路线各有一个优先否决条件。** Tunnel 侧验证断开连接器再接回同一个持久 origin 后，原回执是否仍可查。Containers 侧销毁容器并丢弃原盘，同时让旧写者尝试提交；若丢失任何成功回执或接受旧写者，则存储设计未成立。Workers 侧打断对象内等待，并在创建或轮换的跨对象步骤间注入失败；原客户端能否在正确的凭据版本下恢复原操作，是架构取舍的依据。[Tunnel 专题](tunnel.md) · [Containers 专题](containers.md) · [Workers 专题](workers-do.md)

## 容量与费用要测哪些量

20 秒是协议允许的最长等待。既有直连 supervisor 对空闲 Agent 发出的 claim 实际最多等 1.5 秒，循环间隔约 350 毫秒，每个 supervisor 另有约 12 秒的心跳。假设持续空闲、没有网络和调度开销，单个在线 Agent 每天约产生 4.7 万次空 claim（86400 ÷ 1.85）；这是从代码得到的量级示例。显式 listen、活跃回合、重试和新 daemon 的宿主级 control poll 有各自路径，需分别采样。[宿主常量与主循环](../../src/cloud/client/host.rs) · [显式 listen](../../src/cloud/client.rs) · [控制租约周期](../../.controller/cloud-daemon/wire.md)

对同一组主机、空闲 Agent 和消息量，至少留存入口请求数、并发等待、单 scope 峰值、每次发送至确认的 p50/p95、重连后排空时间、存储读写和保留量。Tunnel 另记主机、磁盘、备份和维护工时；Containers 记运行资源时间、持久后端调用和跨边界往返；Workers 记 Worker / DO 调用、对象活跃时长、存储和管理概况的跨 scope 查询。费用用当日计划和实测量折算。凭据及正文从观测样本里去除。
