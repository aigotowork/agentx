# 空闲时，AgentX 需要问云端什么？

对个人或小团队的间歇性负载，优先削减空信箱查询。真正要同时满足的是：有消息时及时送达，没消息时对象可以安静下来，主机掉线时控制操作仍有明确结局。月账单取决于账号总量；若仍在内含额度内，少查主要是在释放容量和减少写入。[费用口径](paid-do-budget.md)

| 工作 | 目前为何发生 | 云端候选策略 |
| --- | --- | --- |
| 收件 | 旧直连宿主的空闲 Agent 等待最多 1.5 秒，再间隔约 350 ms 查询；显式 listen 有自己的路径 | HTTP 兼容客户端可在连续空结果后退避并加随机抖动，收到消息后快速排空。新客户端可让每台主机在每个 scope 只保持一条可休眠的通知连接，本地唤醒目标 Agent。 |
| 证明主机可以执行 launch / stop | 已验收的原生控制链路约每 5 秒续租，TTL 为 30 秒，控制 poll 最多等 5 秒是当前宿主的设置。租约决定当前安装有无执行权，包括零 Agent 的主机 | 保留租约到期和替换语义。先验证能否合并同一主机已有流量中的续租，再评估更长 TTL。若业务接受“空闲时在线状态未知，操作时重新确认”，还须明确新的操作准入规则。 |
| UI 列表与概况 | 读者需要知道当前状态及数据有多新 | 首次打开、窗口重新聚焦、操作完成或相关变更通知后读取。显示最后观察时间；无人查看时停刷。 |
| 故障恢复与回执 | 超时可能发生在服务提交后，Provider 也可能已经接收 | 断线重连、重启和结果不明时用原 request / claim ID 查证。消息以已提交的记录为准，发送提示和维持连接都不能代替确认。 |

## 当前源码采用的轻量优化

管理控制台的周期刷新已按页面可见性调度。云端收件的宿主循环和显式 listen 现在仅对成功领取到空批次的结果延长下次查询间隔，依次为 0.7、1.4、2 秒，封顶 2 秒。锁被对端占用、正在对账或成功交付后回到 350 ms 的常规节奏。首次查询立即进行；显式 listen 的休眠仍受剩余超时约束。后文的 350 ms 固定间隔和费用算例是改动前的基线。平台通知连接仍是候选设计。[查询调度](../../src/cloud/client.rs) · [宿主入口](../../src/cloud/client/host.rs) · [页面可见性调度](../../web/management/foreground-poll.ts)

## 什么情况下能省时长？

HTTP 长轮询在有消息时可提前返回，延长等待能降低请求数；但只要请求仍在等，DO 就有未结束的处理函数。休眠 WebSocket 可以在所有处理函数返回、没有妨碍休眠的定时器等条件下由平台保留连接并释放对象内存。官方目前描述符合条件后约 10 秒无事件可进入休眠；duration 按计费活跃且不具备休眠条件的墙钟计算，不能把这 10 秒一律加到账单里。如果同一 Scope DO 每 5 秒仍收到续租，它很难获得连续的休眠窗口；即便没有实际休眠，短事件之间具备休眠条件的时间也与挂着 HTTP 等待不同。WebSocket 普通 accept 路径和应用层周期 ping 也要单独评估。[对象生命周期](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/) · [时长计费](https://developers.cloudflare.com/durable-objects/platform/pricing/) · [休眠 WebSocket](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)

按 30 天举例，忽略网络与调度，旧直连每个持续空闲 Agent 约有 140 万次空 claim。如果使用短查询且两次查询起点相隔 30 秒，约为 8.64 万次；没有推送时，均匀到达的消息平均多等约 15 秒才被发现，最差接近一个周期。这个例子仅改变空信箱读取，心跳、重试和业务写入仍需另算。对于需要秒级响应的聊天，单纯拉长间隔的体验代价高；对于无人观看的列表，停刷几乎没有同类代价。[客户端基线](validation.md)

## 休眠通知如何避免丢信？

候选顺序是先提交消息，再对相应宿主发出“有待领取消息”的提示。宿主先建立订阅，再补查待办，以覆盖断线及订阅交界处的消息。重复提示走同一个领取流程；对象被回收后用持久记录和连接附件恢复路由，校验凭据版本、安装与实例，轮换时撤销旧连接。服务在提交后、发提示前也可能故障，即使 socket 看似在线也会漏提示；可先用低频、有抖动的补查或有界重连来限制最长延迟。应用只有在存在明确到期任务时才安排 alarm。通知路径不直接执行 launch，也不确认 Provider 接收。[收件协议](../../.controller/cloud-scope/communication-wire.md) · [DO 设计与轮换](workers-do.md)

## 是否值得改

先对同一批连续空闲和突发来信的宿主，比较现有 HTTP、空结果退避、每主机休眠通知三种策略。记录每台主机每小时空请求、每个 scope 的计费 GB-s、SQL 读写行、发送到领取的 p95，以及故障后漏提示的最长补领时间。增测零 Agent 主机、凭据轮换、提交后断开、租约替换和 Provider 结果不明。只有响应与恢复目标均满足，实测费用或容量收益才值得计入选型。上述云端通知试验待实施。
