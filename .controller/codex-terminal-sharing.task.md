# Codex terminal sharing

The operator should see and switch to a running delegated Codex task in the native Command Center even when its TUI runs in detached tmux. Terminal presentation selects where the TUI runs and how to attach to it. Backend selection independently identifies which compatible native service owns its threads. An AgentX participant still has one exact identity and delivery controller; observing a thread in a second TUI does not create a second participant or controller.

Ordinary foreground and headless terminal launches must keep the Codex client and app-server connected directly. AgentX owns participant identity, collaboration, and delivery; its daemon is outside the Codex request path. A running terminal must still accept prompts and complete model turns when the AgentX daemon is unavailable. The existing protocol bridge remains an explicit integration for special clients; its [terminal pump](../src/integrations/codex/bridge/terminal.rs) can exit on AgentX heartbeat or delivery errors, so the bridge pilot cannot satisfy this terminal requirement.

The [native attach probe](../.docs/codex-activation/acceptance.md#native-tui-thread-composition-probe) verified a first-launch route on stock Codex 0.170.0: send `thread/start` with per-thread configuration, set a legitimate title via `thread/name/set`, then attach with `codex --remote unix:// resume ID` while the setup connection still holds the live thread. The TUI opens with zero turns and no model calls. Closing setup too early still allows resume from disk but loses the tested hook and tool settings. Preserve the configured live instance through handoff; successful `thread/read` alone is not proof the TUI subscribed. No hidden model turn, fake history, global hook installation or relaxed compatibility check is needed.

The integration boundary is a compatible, verifiable service generation and an exact thread/session owner. For a direct launch, bind the native thread to the existing AgentX reservation once. A PTY owns the terminal; the native connection owns the thread. Command Center switches only change what the terminal displays. The existing PTY input path can target the currently displayed thread, so it cannot deliver or recover Agent A by typing into a pane that may now show Agent B. If AgentX needs to wake a shared thread, use the exact native thread key and existing receipt/fence semantics for AgentX's own message input, without relaying ordinary Codex requests. Preserve the documented PTY-based `recover` behavior until a shared path has equivalent safety and capability.

Borrow an already-running native daemon only if the setup can establish compatible per-thread behavior without restarting it or quietly opening a second backend. A parent already on an embedded backend cannot be migrated in place by launching a child. For a future shared default, establish `/new` and resume ownership explicitly: a new native thread must never inherit credentials for an existing Agent just because it was created in that Agent's original pane. Prefer native support for scoped configuration over any relay if stock Codex cannot meet an ownership requirement. Preserve user settings, hook trust and sandbox/approval semantics at setup.

Leave current `/new` behavior unchanged. On a future shared direct path, native `/new` may create a regular Codex thread without AgentX hooks or identity; creating another managed Agent remains an explicit `agentx launch`. Switching back to an existing managed thread retains its own identity. Do not install global AgentX hooks or infer adoption from pane, cwd, or a `thread/started` event. Automatic AgentX participation for `/new` is outside this task.

For AgentX mail, reuse the [activation and receipt rules](../src/messaging/activation.rs) and extract only the necessary behavior from the [native driver](../src/integrations/codex/bridge/driver.rs). A separate connection may read the exact thread's state and send AgentX mailbox input over the native socket. It does not forward TUI traffic, own native approvals, or have a fallback to typing into the pane. Start with threads observed idle; keep active or ambiguous targets pending. Require the exact attachment and native generation, one mailbox consumer, and recorded input evidence before advancing the cursor. A prior idle read is not atomic with `turn/start`; [Codex can accept input into a turn that became active in the meantime](../.docs/codex-activation/protocol.md). The current bridge also sees in-flight user operations, which an independent client cannot assume it sees. Verify concurrent start, approval/input handling, subscription lifetime and unknown outcomes before enabling automatic wake. `recover` requires its own evidence that an eligible failed turn can be continued safely and must never fall back to the currently displayed pane for shared threads.

The [ordinary headless outage case](../.docs/codex-activation/acceptance.md#ordinary-headless-during-agentx-daemon-outage) and the [production direct path](../.docs/codex-activation/acceptance.md#direct-shared-terminal-launch) both pass with real Codex in tmux. The integrated case exercised delegation, one native generation, native Command Center listing, exact bidirectional attribution, active-turn deferral, confirmed receipts, tmux reattachment and continuing prompts during an AgentX daemon outage. The independent native probe covers switching and cross-thread input isolation. Before changing launcher defaults, verify same-thread concurrent starts, approvals, exact recovery/resume, and the supported compatibility scope. A prior idle read remains advisory.

The [Linux bridge pilot](../.docs/codex-activation/acceptance.md#agentx-terminal-bridge-identity-pilot) remains evidence for its explicit private Unix WebSocket entry. It verified parent/child attribution and native Command Center switching on one fixed binary. It did not start a session through `agentx launch --headless` and will not be wired into that command.

Implementation entry: `AGENTX_CODEX_TERMINAL=shared` selects fresh managed interactive Codex launches for the first Linux candidate. `runtime::launcher` preserves the existing reservation and terminal choice and hands verified launch inputs to the PTY runner. `integrations::codex::terminal` owns the setup client and a mailbox-only worker on the same native socket. It creates and names the thread, qualifies the existing reservation as its one attachment, and keeps that connection alive while the direct TUI runs. The worker can stop or fail without closing the TUI connection. One native host registration owns the participant; the PTY in this mode only owns terminal I/O and never registers an injection endpoint or starts the legacy delivery loop. The existing default, explicit resume/fork, other Providers, and PTY-only recover retain their existing route pending direct-path verification. Explicitly selected incompatible native services are reported without restart or silent proxy fallback.

Compatibility investigation during implementation found two distinct false conflicts in the real parent-to-child launch. The child was rebuilding a login shell even though it already had a verified native parent's environment, and the runner had prepended tool directories ahead of Codex's generated PATH helper. The [managed connector](../src/integrations/codex/service/managed.rs) normalizes only the known helper and duplicates, unless the native config declares a PATH dependency. Stock TUI also persisted `tui.screen_reader_detection_done` after its first launch; the connector excludes only that presentation receipt from its semantic server configuration digest. Real environment and configuration differences still reject without restarting the service.

The direct TUI reports launch readiness once through its existing native host registration after the PTY has observed a ready prompt; this event is distinct from the native thread's activity state. The same worker owns AgentX mailbox delivery. It does not register a second controller or write any PTY input. The [opt-in usage](../.docs/architecture/terminal-sessions.md#codex-agent-command-center) and r5 artifact are available for local testing; installed binaries and running services are unchanged.

Default and recovery follow-up: use the direct path automatically for compatible fresh Codex terminal launches. Negotiate before `thread/start`; if automatic attachment is unavailable at that boundary, keep the original PTY launch with its existing hooks and recovery. `AGENTX_CODEX_TERMINAL=pty` forces the original route and `shared` requires the direct route. Once native thread creation is attempted, never retry the launch on another backend. No change to `/new`, resume/fork, or the special protocol bridge.

Recovery keeps the same CLI, failure episode, and durable ticket. Discovery chooses the exact live PTY host or the registered direct native attachment. The native worker checks the original failed turn has ended and the exact thread is `idle` or `systemError`, consumes one ticket before sending `turn/start` with the fixed continuation and its own correlation ID, and confirms only matching recorded input. A real 403 leaves Codex 0.170.0 in `systemError`; this is distinct from an active turn. An uncertain write never causes an automatic second continuation; a later successful model observation clears the error. Recovery and mailbox remain separate even though both use the same native connection. Verify a real terminal 403 followed by one recovery on the original thread while the visible pane shows another session, plus default, fallback, and daemon-outage regression.

Default selection and native recovery are implemented and verified on Linux with Codex 0.170.0. See the [default and recovery evidence](../.docs/codex-activation/acceptance.md#shared-terminals-by-default-and-native-recover). The [final candidate](../.artifacts/codex-terminal-sharing/release-candidate/agentx), SHA-256 `dfbd79a749519c610dd565cf20afddbfe086db9d3e952545027e47b40907fd99`, also confirms the already recorded mailbox input while its model turn still shows the 403. The ordinary PTY fallback, controlled PTY recovery, and stdio root/EOF cases passed during the follow-up. Installed executable replacement and running daemon migration are separate from this result.

## Follow-up from the picker footer incident

In the DancingAI scope, a resumed Codex 0.172.0 session had pending mail and a live, polling PTY host. `agentx term` showed an empty foreground composer at row 47, while a quoted `enter select · esc back` line at row 26 made the whole-screen picker matcher return `ready=false`. A second resumed session displayed that same footer below a real picker. The [PTY correction](../src/runtime/pty/screen.rs) distinguishes these frames without removing the gate. The incident replay failed before the correction and all 104 screen tests passed after it, using a disposable target and temporary directory. Both sessions use the legacy resume route. The same scope also logged fresh launches falling back because [direct terminals require 0.170.0](../src/integrations/codex/terminal.rs); these are two independent gaps in coverage.

Follow-up boundary: preserve the native TUI as the input owner for interactive Codex sessions. Its dispatcher resolves slash commands and preserves the current mode and compose state. Do not replace terminal mail wake with an externally issued `turn/start`. The existing [PTY host](../src/messaging/delivery/host.rs) submits a wake marker; the [Codex prompt hook](../src/integrations/hooks/codex/client.rs) delivers the message content and confirms the existing receipt. Ordinary mailbox text must not acquire slash-command semantics. The [existing direct integration](../src/integrations/codex/terminal.rs) remains a distinct path; no change to its launcher defaults or live sessions is authorized by this follow-up.

For stock Codex, a bounded next step is one typed snapshot of the active input surface rather than independent screen-wide readiness and emptiness checks. Use provider hooks for exact session and turn facts. Use the current caret/composer frame for local input evidence and classify a visible draft, active overlay, or unknown state separately. Approval/title signals may veto submission; their absence does not prove focus or an empty draft. Planning mode itself is independent of whether its composer is ready; a plan confirmation dialog is a different input target. Recheck the observed frame and user input sequence at the PTY's own write boundary. These observations still cannot prove eligibility for a pane that can silently switch its active thread. When the target or input surface cannot be established, keep mail queued and report why.

Scope is AgentX's recognizer against stock Codex; a Codex-side change is out of scope. The PTY incrementally maintains the visible VT grid. `term` dumps that same grid on request; normal admission reads local `ScreenState`, not transcript history or `term` JSON. The [current updater](../src/runtime/pty/shared.rs) repeatedly materializes the visible grid for readiness, approval fallback and prompt extraction even though they describe one input surface. The [bounded scrollback](../src/runtime/pty/screen.rs) is for exit diagnostics, not ordinary readiness. Separately, the daemon polls unread events after the exact recipient cursor (at most 50 returned), and a rare [stale turn recovery](../src/transcript/codex_completion.rs) reads a bounded transcript header and tail. Neither is the source of the picker false positive. Verify a shared composer observation with historical picker output, real pickers (including slash and plan confirmation), an idle Plan composer, drafts and attachments, user input racing wake, pane switch, and lost receipts.

Retained evidence for the separate direct route: a two-connection Unix socket probe on stock 0.172.0 with a disposable home and loopback model reproduced the [known admission race](../.docs/codex-activation/protocol-feasibility.md). After the mailbox connection read `idle`, the user connection held a turn open. The mailbox `turn/start` then returned that same turn ID and its correlated input appeared in the user's turn. This is why an idle provider read alone cannot establish terminal input eligibility or enforce idle-only native admission.

Implementation: the [screen tracker](../src/runtime/pty/screen.rs) caches one observation of the current Codex composer and approval fallback, bounded to the bottom 16 visible rows in ordinary operation. Observations with no clear composer, an active menu, or a draft cannot authorize a mailbox write. [The PTY write guard](../src/runtime/pty/inject.rs) checks the current frame and user-input revisions for the fixed marker and the later Enter. A local screen transition can wake [the pending worker](../src/messaging/delivery/host.rs); it refreshes the exact recipient before an eligible write. While the local gate stays closed, it uses an absolute three-second daemon Poll deadline, including when notifications repeat. Write acknowledgments do not confirm mail. The existing cursor receipt, recovery ticket, and unacknowledged-wake latch still own those outcomes. This is a source change; installed executables and active PTY processes keep their loaded behavior until separately adopted.

Verification on Linux: 245 PTY tests and 80 delivery tests passed. The controlled Codex ordinary-send case observed no input while the real picker frame was focused, then one submission and a hook receipt about 74 ms after the picker frame cleared, with its old footer still on screen. It also verified queued mail across daemon reconnect and resume, and an accepted message that remained pending without automatic resubmission when no hook receipt arrived. Controlled Codex explicit recovery, missed-Stop reconciliation, and Qoder delivery/reconnect passed on the same product artifact (SHA-256 `292bb7dfa9cfba5e1a399857a99d1a8f2112057dac3479f621f1f72d3411f31e`). Windows GNU cross-compilation passed; native Windows runtime behavior was not exercised.
