# Experience design

## Outcome and professional basis

Advance the [Delivery user result](../delivery.md#用户结果): the user can define work, organize real Agent collaboration, find the next action, inspect outputs/checks and accept the result. You are the product/UI designer, not an implementer of the old diagnostic interface. Read [team entry](../AGENTS.md), [design entry](../../../.docs/collaboration-workbench/README.md), required interface guidance, and management-product-design README/workflow/page-design as relevant. Establish your method and record important design reasoning in the owned experience document.

## Design responsibility

Current phase: the user finds the revised resource-workspace direction broadly suitable and requests detailed resource, operation, component, state-style and layout design before implementation. Preserve the revised resource structure and compact visual principles. Read [the shared standard](../../../.agent-guides/scenarios/interface-design.md) and [the detailed-design assignment](../controller.md#resource-operation-and-component-detailing). Earlier rejection/redesign notes below remain history, not an instruction to restart the main information architecture again.

Start from user jobs and information relationships, without inspecting/copying the current Web layout as the design premise. Choose an effective working subject, navigation and contextual disclosure. A representative scenario is a small real repository feature implemented by one Agent, independently checked by another and explicitly accepted by the user; an in-progress task needs human input. You may refine the scenario and layout professionally. Do not treat a task board, chat feed or card dashboard as a mandated solution.

Supply one recommended cohesive direction with realistic Chinese design content, explicit example-data attribution and sufficient density. Keep the main desktop workspace within a practical viewport; use drawers/popovers/dialogs when they preserve context. Make assignment, who-is-waiting, output/check evidence and acceptance understandable. Keep diagnostic infrastructure secondary. Include the necessary empty/loading/failure/needs-input behavior in the interaction explanation rather than drawing every peripheral case.

## Current detail deliverable

The four main SVGs establish the overall composition, not complete interaction/component coverage. Own the professional gap assessment and fill important details in `.docs/collaboration-workbench/interface-details.md`, linked from `experience.md`. This document owns detailed interaction/component decisions; retain scenario S1–S5 and native meanings at their existing sources rather than copying them.

1. Inventory the actual resources and actionable controls in the revised offering. For source/work navigation, task editing/assignment, Agent selection/detail, task messages/questions, result/artifact references and check/history/acceptance, specify the real entry, fields, actions, result/return, meaningful unavailable states and capability basis. Distinguish current native support, selected target and deliberately deferred behavior. Every visible action needs a defined outcome; avoid a fake icon-only shell.
2. Detail the important work paths, not just the happy-path frame: create/edit with dirty draft and validation; valid/invalid role selection and rebind; saved versus dispatched; question answer versus ordinary note with correct recipient; result/history/current-basis check; failed/unable check, request changes/recheck and acceptance. Explain preserve-context behavior on switch, close and return. Operator browser actions must not impersonate Agent result/check publication.
3. Define the shared visual/interaction vocabulary for actual states: loading versus refreshing retained data, initial-empty versus filtered-empty, selected/hover/focus/disabled, saving/pending, rejected/failed versus unknown command outcome, reported/verified/accepted, unavailable collaborator, stale basis/conflict and read-only service. Use concise contextual feedback with actions and consistent icon/color/shape, not explanation banners. Do not draw every Cartesian combination or invent a global state framework.
4. Establish cohesive Layout → Blocks → Components boundaries for the planned React consumer. For each meaningful unit give purpose, inputs, emitted user intent, owned ephemeral state and explicit exclusions. Document shared semantic token roles and component variants, keyboard/focus/Tooltip/touch behavior, scroll boundaries, constrained desktop and narrow adaptation, long names/paths and populated-list behavior. Do not create a generic component platform or a premature registry/Storybook service.
5. Add a bounded set of editable SVGs that makes the previously undrawn core resource views and high-risk operation states reviewable, plus a compact component/state reference sheet. Prefer a few coherent composed scenes over a screenshot for every minor case. Keep the existing four overview states stable unless the detailed design reveals a real inconsistency; explain any required revision. All examples remain illustrative and icons have usage labels.
6. Map the detailed decisions to existing Web/native/independent-acceptance Tasks and the Delivery outcome. Record concrete semantic gaps with the controller; layout/component choices remain yours. Complete on a usable implementation handoff with actual SVG references, state/action/component coverage and explicit unresolved/deferred remainder. No production implementation or new approval/review cycle is implied.
