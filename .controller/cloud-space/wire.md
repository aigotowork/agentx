# Cloud Space implementation contract

Native: nohuze. Space Web: nesaze. Base: `origin/main`. See [native Task](native.task.md) and [Web Task](web.task.md). Browser delivery does not change installed or deployed services.

## Entry and credentials

`GET|HEAD /scopes/{id}/space/` serves the embedded Agent Space index for a syntactically valid scope ID. The shell is public and contains no scope data or credentials; existence is learned only through authenticated APIs. `/scopes/{id}/space` redirects to the canonical path, preserving only valid nonsecret navigation values. Embedded resources use absolute, same-origin `/space/…` paths; missing assets return 404. No wildcard SPA fallback or local Management/host API projection. The Cloud deployment console at `/deployment` links the selected scope to `/scopes/{id}/space/?access=admin`; Cloud Space links back to `/deployment`. `access=admin|scope` is an optional presentation hint only. Exact selection uses the query tuple `host`, `name`, `incarnation` on the scoped entry. Links produced by Space may include the nonsecret generation to fence an exact selection; without it, the frontend binds selection to the current descriptor. No URL or bootstrap payload carries a bearer. Browser login offers page-only, 30-day and 90-day retention. Remembered admin access is shared with Deployment on the same origin; member credentials are keyed by scope. Restore revalidates the bearer without renewing the fixed deadline. The user explicitly chooses and supplies one bearer; contact the same origin only. Serving the shell does not admit an API request. The Space CSP restricts scripts and HTTP connections to its origin; images/fonts permit in-bundle data where needed. HTML, errors and API responses use `no-store`; fingerprinted bundle assets may cache immutably.

The admin browser submits operator messages. Inbox claims and host enrollment belong to the native participants. The scope bearer establishes membership, and browser selection of an identity is never Agent authentication. The admin launch initial prompt is the existing supported way to start new work; it is not a message to an existing Agent.

## Read-only cloud mailbox history

`GET /scopes/{id}/api/v1/messages?generation=…&host=…&name=…&incarnation=…[&before=…][&limit=…]`; operation ID `scopeListMessages`. Native owns the OpenAPI and generated SDK method `scope.listMessages({generation,host,name,incarnation,before?,limit?}, opts?)`, returning `{items:MessageView[],next:string|null}`. A matching scope bearer and current generation are mandatory; query from an admin bearer, an unrelated scope bearer, or from a rotated bearer is 401. Stale generation is 409 `stale_generation`; unregistered exact tuple is 404 `not_found`; invalid syntax or bounds give 400 `invalid_input`. A registered tuple with no messages returns 200 with an empty list. An exact retired tuple remains readable if selected directly; no fallback to its replacement. Rows include real durable accepted cloud messages addressed to/from the tuple, including messages awaiting delivery, newest first by decimal-string message ID. They are not Provider turns and do not prove delivery. `before` is an exclusive positive decimal message ID; omit on the first page and pass `next` verbatim for older rows, until null. Default 20, maximum 100, up to 1 MiB of UTF-8 body bytes per page. `MessageView` otherwise reuses the existing representation, including bigint Unix seconds in the SDK. No claim or receipt state is written by this read.

The native boundary routes finite assets and scoped API calls. The communication store owns exact identity filtering, bounded SQL, generation and credential fencing. The SDK owns lossless decoding of native rows; Web owns selection, render and navigation. The cloud defines a reserved sender for operator messages.

## Web navigation fence

Space writes `generation` with the exact selection query to keep copied links tied to the authenticated scope generation. An exact tuple pasted without a generation binds to the authenticated generation; a mismatched generation is reported and never resolves to the replacement. `view=list` remembers the roster presentation. These are nonsecret presentation parameters; page routing remains independent of their values.

Implementation shape: `cloud::space` owns finite HTML/asset routing and response policies, `cloud::communication` owns the GET method and its typed query, and `communication::store` owns an indexed read ordered by message ID. Existing scope databases need additive sender/recipient indexes so a sparse history page does not scan the mailbox. Deployment initialization upgrades these indexes while it owns the catalog lock; no data or protocol epoch changes. The Deployment scope header owns a single same-origin navigation link and reuses the active visual tokens.

Member and operator routes authenticate their own bearer. Browsing history uses a side-effect-free read. The browser sends on behalf of the authenticated operator.

## Operator conversation for the shared Space

The deployment admin client reads and writes `/api/v1/admin/scopes/{id}/messages`. GET takes the same exact selection, generation and cursor as scope history. POST takes `{generation,request_id,to:{host,name,incarnation},body}` and returns the persisted MessageView. The server supplies the operator identity, fences the destination, and deduplicates exact retries. A successful write means accepted into the target mailbox. An Agent response is another persisted message from that exact instance. A lost response can be reconciled by replaying the original body and request ID. The browser never retries an ambiguous write under a new ID automatically.

The cloud Agent host forwards the visible final answer of a completed Codex turn to the operator who initiated it. The host matches the thread, turn and recorded user input before sending an acknowledgement linked by `reply_to`. An already persisted explicit reply to that request satisfies automatic forwarding. Hidden reasoning and tool output stay on the host. Replies exceeding the message limit are truncated at a UTF-8 boundary and marked. New cloud Agents need the updated host executable for automatic replies. Previously launched processes keep their original behavior.


## Exact Codex records and Agent facts

Both existing browser access modes read the same projection: `GET /api/v1/admin/scopes/{id}/transcript` (admin bearer, SDK `listTranscript(id, query, options)`) and `GET /scopes/{id}/api/v1/transcript` (scope bearer, SDK `listTranscript(query, options)`). Pass `{generation,host,name,incarnation,before?,after?,limit?}`. The latest page and exclusive `before` pages are newest first; exclusive `after` pages are oldest first. An empty reader follows with `after=0`. Limit defaults to 20 and is capped at 50. The response is `{agent,available,items,next,latest,facts}`; verify the returned Agent address. Items are `{id,role,text}` with decimal-string IDs. Follow `next` in the chosen direction, and use the last consumed ID as the incremental watermark. `latest` is the exact persisted head at the time of that page. An exact registered Agent with no host projection returns `available:false`; a missing exact address returns 404. Registered retired identities remain readable without resolving to a replacement. Old deployments may lack the route.

The exact supervisor projects user text, visible Codex commentary and final text, and constant categories for selected tool starts. It discards tool names, arguments and output, attachment contents, hidden reasoning and moderated hidden text. It removes known local credentials and common credential formats, clips UTF-8 text to 8 KiB per item, batches at most 12 rows, and publishes only changes plus a lightweight fact renewal on its existing scope connection. Opaque credentials embedded in arbitrary plain text cannot be identified solely from their spelling. Managed daemon IPC admits this publish command only from the exact supervisor process. Scope storage also checks the bearer, generation, host installation, exact current registration and bounded input. It deduplicates Provider items and retains up to 256 records per exact instance and 20,000 per scope. A recovery makes one bounded Provider tail read; normal updates are driven by Provider notifications. No browser endpoint exposes raw Provider records.

Request `facts=true` on either roster to receive `facts:{role,title,cwd,status}` where a host has reported them. Role is the adopted role, title follows the Codex thread name, and cwd is the launch directory. Status reflects the Provider: `active`, `idle`, `error`, or `unknown`. The server returns `unknown` after 75 seconds without a fresh report and `stopped` for an exact retired registration. Facts and projected transcript are supplied only by updated supervisors; old registrations remain addressable. The scope emits a Transcript change only after a committed change, and also emits a roster change when facts change. Space opens the exact successful launch receipt on Transcript and follows it by incremental reads.

## Visible Space change subscription

Both authenticated API bases expose GET `/changes?generation=…`. The first read returns a process epoch and independent directory, message and transcript revisions. Pass `cursor=epoch.roster.messages.transcript` to wait up to 25 seconds. A commit wakes waiting readers after it becomes durable. Timeout returns the same small revision object. A different process epoch invalidates cached watermarks. Waits hold no SQLite connection. Credential rotation revokes waiting scope readers. The deployment reserves 16 concurrent browser waits and reports capacity exhaustion for clients to back off.

A visible Space owns one cancellable subscription. Directory changes refresh the loaded roster, message and transcript changes catch up the selected exact reader. Message `after` reads only IDs above the exclusive watermark, in ascending order. `0` starts forward reading from the beginning. Older pages keep using exclusive `before` in descending order. Launch/stop receipts can be read directly while pending. Visibility changes cancel the wait and revalidate on return. Host options refresh on opening the launch dialog. A legacy deployment without the changes route uses a slower selected-message probe.
