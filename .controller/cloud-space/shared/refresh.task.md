### Request baseline and compatibility probe

On the shared Cloud Space baseline, the 5-second [workbench timer](../../../web/agent-space/src/cloud/workbench.ts) reloads every loaded member and host page plus all visible conversation readers; unresolved receipt checks share the same interval. The [directory adapter](../../../web/agent-space/src/cloud/model.ts) reads the scope immediately before and after **each** inventory page. For an admin that calls [scope summary counts](../../../src/cloud/admin.rs), not a lightweight descriptor. The local browser fixture observed **9 GETs in 6.2 seconds** after two member pages and one host page were loaded, without a conversation or pending receipt: 6 scope summaries, 2 member pages, 1 host page. This distinguishes browser fan-out from provider or host traffic. Total deployment traffic and server time per route were not measured.

An isolated legacy-server fallback candidate ([patch](/tmp/agentx-cloud-space-refresh.uwoYOC/legacy-fallback.patch), based on `ac1e4c8`) observed **0 GETs in the same window**. It reads inventory on demand, fences each complete directory read, follows only the selected foreground conversation every 15 seconds (one-row head probe once seeded), and schedules pending receipt lookups separately. The full Cloud Space fixture passed through automatic launch receipt and roster update, incoming reply, reload, exact stop, and member history. The existing native conversation fixture also passed. The candidate is retained separately from the active implementation so it does not compete for the browser adapter or transcript files. It leaves the current API intact and still transfers one existing row in an idle nonempty reader; it is evidence for compatibility, not an implementation of server-side waiting.

For the modern path, compare requests and response bytes for a settled visible tab at the same loaded pages, then commit one exact message and confirm one scoped wake plus incremental reads. Also rotate a Scope bearer during a wait, reconnect after a server restart, and hide or close the tab while waiting. The current Cloud Space fetch timeout is 15 seconds; match it to the selected server wait so the timeout path is intentional. The existing host `/inbox/claim` wait can inform subscribe-before-read and cancellation, but it changes mailbox state and is not a browser reader. Native host heartbeat and claim traffic are independent of the browser measurement.

### Implemented behavior and integrated evidence

The authenticated [wire](../wire.md#visible-space-change-subscription) and [browser watcher](../../../web/agent-space/src/cloud/changes.ts) implement one 25-second wait per visible page with a 35-second transport deadline. Message invalidations consume only forward rows after the exact conversation watermark. Directory inventory and host capabilities are loaded on demand. Older deployments retain the selected-reader probe. A hidden tab abandons the wait. An invalidation arriving during another latest-page request queues one catch-up to avoid missing the last message.

The real Chrome, TLS, native daemon and Codex test used a finite loopback Responses model. During its settled 27-second interval, the only two API requests were the change subscription and its renewal. No host/member pages, scope summaries, conversations or transcript bodies were fetched. A separate turn held its final answer until Chrome rendered the public commentary.
