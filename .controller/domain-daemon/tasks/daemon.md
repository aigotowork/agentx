### Unfinished work and next implementation

The tree is intentionally incomplete at this migration boundary: `daemon/mod.rs` declares `server` and `transport`, but **`src/daemon/server.rs` and `src/daemon/transport.rs` do not exist yet**. `service/client.rs` imports their intended functions; memo owns the shared `service/mod.rs` client export. Implement `transport::{probe,acquire,call,shutdown}` and `server::run` against the existing native declarations, rather than replacing the service boundary. Intended server shape: bounded Unix connection workers perform Hello + one operation, send typed jobs through a bounded queue, and the serving thread alone calls `Application::handle`. Queue admission and dispatch recheck deadline, daemon instance and expected database generation. Set `RequestContext.process` from `platform::peer`, never from the request body. Workers may wait only to an absolute operation deadline; a missing reply after potential dispatch is OutcomeUnknown. Shutdown stops admission, drains the currently admitted application operation, closes socket, drops application/database, then releases scope lease. Remove stale sockets only while holding scope ownership; do not unlink the lock file. Full worker/queue handling and socket ownership cleanup are not implemented.

Intended startup shape: client probes a compatible ready endpoint; serialize auto-start with a separate retained scope startup lock; use the same current executable with `daemon serve --scope PATH`, detached existing process helper and null stdin/stdout/private stderr log. Do not infer readiness from spawn/PID/path existence. Explicit daemon scope entry must precede project direnv/client identity setup. A bounded acquisition deadline observes startup/initialization failure, and existing incompatible daemons are left running. Do not replay an application operation after a write failure or lost response. Client handles may reconnect to a new daemon incarnation only while the retained database generation matches.

### Peer incarnation contract and relay handoff

`sys::process::identity(pid)` is source-defined as: Linux/Android `linux:<boot_id>:<start_ticks>` from `/proc`; macOS/iOS `apple:<start_sec>:<start_usec>` from `proc_pidinfo`; Windows `windows:<creation FILETIME>` from `GetProcessTimes`; other Unix uses a `ps lstart` fallback for non-IPC callers. Any query/access/race failure returns `None`. Local `platform::peer` authenticates same-user PID/UID on Linux/Android and macOS/iOS, then attaches this best-effort identity; its unsupported other-Unix branch fails before peer creation. Windows named-pipe peer validation requires a nonempty observed incarnation and rejects otherwise.

A `CallerProcess` with an authenticated PID but `incarnation: None` is authenticated as a same-user process endpoint, not as a reusable process ownership proof. Domains admitting external host effects must require `Some(nonempty)` and must never authorize `None == None`; pure reads may choose a weaker observation policy. For persisted relay owners, `Some != Some` is stale; `Some` versus `None` is unknown/stale for effect admission; `None` records cannot be taken over unless positive `has_exited(pid)` evidence exists. `is_alive` false or identity-query failure alone is not positive exit evidence. Relay owner received this exact matrix; no daemon transport edit is required.
