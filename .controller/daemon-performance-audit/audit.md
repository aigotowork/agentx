# AgentX 性能设计审计

本轮审计实际工作树和已保留的事故证据。磁盘运维另有负责人。已有隔离任务负责写者和读队列、文件投影、诊断日志和 Space 信箱重复读取的集成；这里记录其余路径的设计证据和先后顺序。源码和隔离实验都不代表线上已经替换或达到某个延迟。

## 从用户动作追到实际工作

| 使用场景 | 源码证明的重复工作或规模风险 | 首选改法与不能丢的语义 |
| --- | --- | --- |
| `send @name` / 发线程消息 | [接收事务](../../src/messaging/service_store.rs#L175)先算路由判断广播是否已确认，[持久化](../../src/messaging/submission.rs#L87)又算一遍。两次都加载可投递名单；线程分支可能两次扫 KV 并排序。持久化还按收件人逐个读完整 Agent 行，只为生成精确会话引用。 | 同一个写事务内先冻结路由计划，提交事件、场景寻址和回执共用计划。把正文的收件意图和自动追加的 bundle 摘要分开验证；覆盖广播确认、精确本地名、远端歧义、human、线程、回复继承与重放。先去掉第二次路由、缩窄收件人投影；精确寻址只做必要查找，再用稀疏与广播放量分测。 |
| `agentx list --names` / 查单个 Agent | [CLI](../../src/cli/commands/list.rs#L115)先请求完整 Listing，本地才按工作区和输出形式裁剪；[Listing](../../src/service/listing_store.rs#L13)在写事务中执行回收、补启动失败信息，再装配未读、标签、绑定、状态、端口和停止历史。给 `target` 并不会缩小普通 Listing 的记录装配范围。 | 为 names、单个 Agent/字段和自动化筛选选现有或新的轻量只读结果；过滤先于水合。把安全收尾与普通读解耦，复用独立维护入口及过期判定；保留显式清理、准确存活状态和已提交后才允许的宿主效果。 |
| 打开 Management 或 Space 后无操作 | [Management](../../web/management/use-management.ts#L52)每次循环重新请求 Descriptor 和已加载的所有 roster 页；选中 Agent 的详情和消息还各有一次请求。快请求时三页加一个已选会话约六次请求/轮，接近 3 次/秒/标签页，未计挂起回执。实际周期是耗时加 2 秒。Space 的 [3 秒刷新](../../web/agent-space/src/live/controller.ts#L151)在 overview 模式也重读前 N 页；选定办公室已经按需加载成员，信箱前缀复用已有实现。 | 状态新鲜度按视图需求定义。隐藏页降频/暂停，恢复前台和操作成功立即刷新；历史分页只按需读。把低变化的 Descriptor/配置与活跃数据分开；优先试单个可合并的分区变更标记，没变化时不做重 SQL，细节和消息按独立游标读。先测同一标签页，再考虑同作用域跨标签页合并。HTTP 304 若先完整计算结果，只省网络，不省 daemon 工作。 |
| 浏览器查操作回执 | [Operation 查询](../../src/management/store.rs#L552)会调用 [reconcile](../../src/management/store.rs#L47)：探测执行进程，在需要时写 Unknown。因此它目前不是纯读，定时查回执仍会进写队列。 | 计量后再拆：普通读只投影已提交回执；过期判断由有限后台工作或专用核对触发。仍需保留不可重放、旧 worker 不被误夺权和结果未知的语义。 |

## 表与索引的判断

| 数据及粒度 | 设计问题 | 候选方案和验收 |
| --- | --- | --- |
| `events`：带序号的历史事实和 JSON 内容 | 适合保留历史事实；不适合每次从长历史反查收件人、停止会话、最新状态等热关系。[未读批量查询](../../src/service/listing_store.rs#L136)一次扫最旧游标之后的所有消息；一个旧游标就决定整页成本。 | 优先减少哪些页面需要精确未读数。确需精确且实际以稀疏消息为主时，再加 `(recipient,event_id)` 的接受关系投影，可只读各自游标之后的记录。保持 `delivered_to` 的历史口径：它不同于按规则可投递的 `hook_mailbox_routes`，也不同于实际消费的 receipt。新增索引带来广播写放大；与只显示有无、按需计数、按活跃期间增量维护比较。停止历史用合适的部分索引先试阅览/工作区两条热点查询，核对部署后的实际查询计划。 |
| `kv`：不同领域的精确键值与状态 | 精确键查询适合小配置或单个回执；多个领域用前缀和 JSON 反查，把自身操作成本绑到无关数据。已上线的三个订阅索引没有覆盖 [线程成员查询](../../src/db/subscriptions.rs#L492)；成员写入也会为每封线程消息重写同名 JSON。 | 短期先用可验证的局部索引隔离线程访问；若成员的查询、写入和维护都热，再把线程成员建成明确关系。先校对成员顺序、重入是否应更新顺序、已退出成员和同名重用。回执不因移出 KV 或减少空间而改变保留期限或自动重试保证。 |
| `instances`：当前 Agent 快照 | 名单和路由只要少量字段，却常使用整行或逐个查。历史、短时进度/心跳、当前授权和 UI 投影的生命周期不同。 | 先缩窄查询和合并必要读写，测一条工作事件真实写了什么。若高频诊断字段成为写入热点，可降频或在内存保留近期观测，明确重启后的未知；持久身份、游标、投递确认和恢复票据不能由缓存授权。当前写者、只读快照和历史事件各保留自己的职责。 |
| `events_fts` 和多种派生投影 | 每插入一条事件都会触发 FTS（见 [事件触发器](../../src/db/mod.rs#L543)），消息另有多个派生路径。单个索引能提高读性能，但多投影叠加可能提高写入成本。 | 用同一夹具分别记录追加一条消息、状态和广播的写入次数、WAL 字节和现存搜索命中。只有确认某类数据不属于当前全文搜索合约，才考虑减少索引内容。保留事件序号和可追踪性。 |

## 隔离证据与实施顺序

[探针](probe.py)用实际扫表的 SQL 和候选 SQL 在临时内存库比较，输出[数据、结果和查询计划](workload.json)。SQLite 指令计数的粒度为 100，显示 0 代表低于 100；不包含 Rust JSON 解码，也不能换算为生产延迟。

- 10 万条消息、4 个目标与不同游标：稀疏时旧 SQL 返回 10 万个 JSON 字段、约 70 万条 SQLite 指令；关系索引返回 4 个计数、约 500 条。密集时 SQLite 仍要执行约 65 万条指令，关系表增加到 30 万行；它确实省去了搬运和解析 JSON，但不能仅看稀疏收益决定所有写入路径。夹具含重复收件名字，并逐项比对计数。
- 线程 `a` 最终只有 2 个在场成员；27.2 万条无关 KV 让旧查询执行约 108.8 万条指令（另需读取在场名单）。候选的两个索引查找不到 100 条，保留成员与顺序。生产在线迁移和写入侧成本仍待验证。
- 停止历史只返回 12 条时，10 万条 `life` 仍让旧页消耗约 60 万条指令。创建部分索引后，默认计划仍选旧 `idx_type`；隔离库补齐统计信息后才走新索引，同一结果约 100 条指令。验收要看实际查询计划，而不能看到 schema 有索引就算完成。

**首批**：同一事务只路由一次，单独核算 `Submit` 的路由、写入与提交后时间；旁路 `list --names` 的维护和完整水合。接入既有隔离任务的详细标签、排队阶段与读写队列计数，先确认用户体验没有依赖被删掉的副作用。**第二批**：减少可见页面的全量重复读和隐藏页面负载，压测分页多开；然后按实测选择线程查询索引和停止历史索引。**第三批**：用实际的稀疏/广播分布判断是否给接受关系建表，再评估回执、FTS、历史的保留与写放大。不要先加一层通用缓存或换数据库。

基线与验收用同一构建和同一可重复负载：空闲单页/多页/后台标签；精确发给一个 Agent/线程/广播与重放；历史增长 10 倍但当前集合不变；管理读被卡住时 Hook 和消息；历史投影回填未完成及代次切换。分别记录客户端每动作请求数、daemon 子操作/排队与拒绝、读写 SQL 工作量、每封消息的附带写入和返回字节，再记录 P50/P95/P99。判定优化的首先是结果一致和成本不随无关历史增长，其次才是上线后的延迟变化。
