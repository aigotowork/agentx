The incident's single dispatcher serves both PTY mail coordination and unrelated requests. The live log sample contained 7,810 `delivery.snapshot_failed` rows, all Busy, among roughly 2 MB of log. SQLite query plans confirm full KV scans for the old subscription and request-watch selectors; the existing subscription-index rollout has separate ownership. The same sample shows slow Management and post-commit hook calls, so reducing PTY pressure does not establish that SQLite writes caused the original stall.

The PTY delivery loop owns polling cadence. Reuse a freshly resolved snapshot within an iteration, refresh once after an idle/notification wait, and check the exact participant before pressing Enter. Screen-only wait phases stay local; cursor verification polls at a capped cadence. Failed snapshot RPCs back off with a bounded per-host delay that notifications cannot bypass. Keep the existing wire types and delivery evidence. Persistence uses the resolved row's cursor and requests the first bounded delivery window through the existing indexed mailbox path; read only one eligible row when a gate needs a boolean. Healthy delivery and recovery authority remain separate.

The legacy steady idle path made five Poll calls per cycle and published two endpoints even if unchanged; the repaired steady path makes one Poll per idle wait and restores each endpoint only when the latest snapshot shows it missing or changed. The screen loop could approach 200 Poll calls/s before RPC latency (two calls per 10 ms iteration). Unchanged screen rendering now has zero Polls, with fresh checks on submission; awaiting cursor progress polls at most about four times per second. Repeated snapshot failures settle at one retry per 4–4.25 seconds per host, with one diagnostic per continuous failure spell.

The sampled project scope had 272,432 KV rows and complete inferred mailbox-route coverage (`65288/65288`). A separate in-memory SQL fixture used the actual legacy and indexed SQL over 20,000 message events, 2,000 eligible, and read 20,000 versus 50 payloads (~140,000 versus ~1,400 SQLite VM instructions; no production latency claim). Without route coverage the fallback still scans past unrelated rows as needed to find the bounded window. A fresh `CARGO_INCREMENTAL=0 just test --bin agentx message_delivery -- --test-threads=1` passed 3 cases (one real-process acceptance case was not run); the same binary passed all 79 focused delivery/module and mailbox-index tests. No installed binaries or live daemons changed.

Remaining daemon isolation work: evaluate the subscription-index rollout separately; replace the human mailbox count's scan of message events and per-event `json_each` with an indexed candidate path that preserves historical address semantics. Office activity also pays that mailbox count on every poll. Keep file-binding enrichment and best-effort dispatch logging off the SQLite request path, then evaluate a bounded read-only lane with generation fencing for slow Management queries. Measure dispatcher queue time, actual completion, and I/O pressure separately. Keep SQLite durability and live resources unchanged during this source repair.
