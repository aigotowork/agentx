## Composition and effect order

1. Existing project preparation resolves cwd, effective env, Codex home and the pinned executable before identity/config reads. Only a supported app-server invocation selects this integration. Native version queries, ordinary Codex PTY and other providers retain existing dispatch.
2. Acquire a compatible shared backend via `CodexService`. `ExecutionId` identifies its stable observed generation. A fresh `AttachmentOwnerId` identifies this one proxy/control owner; it is not the backend identity. The connection owns no daemon-termination authority.
3. Carry the existing launch ancestry, initial cursor and launch context into qualified root preparation. Reuse `names::generate_unique_name`, `binding::initialize_instance_in_position_file` and the existing launch initialization semantics; do not reference the absent historical `create_instance_position` helper or create a process-default binding. The bridge and reko coordinate any required extraction. Read `canonical_participant` before resume to prepare the canonical identity. A previously unregistered native resume reserves a provisional participant and carries it in the generic/native resume intent; an existing scoped canonical identity remains authoritative under the atomic recheck. Create/fork reserve their own participant before native submission; failed/unknown root results do not qualify a binding.
4. Preserve caller initialization/capabilities. Correlate each successful outer create/resume/fork; attach with the returned canonical home/thread, backend generation and controller token, then select `DeliveryMode::NativeInput` before releasing the root response. Native internal threads never attach merely by emitting events. A fresh binding token fences old callbacks.
5. Hook/session tools resolve known home/thread/generation against attachments first. Bootstrap is announced per thread only after successful output flush. Native-input attachments keep hook identity/status but suppress hook mailbox consumption. Explicit listen/inline output can contend on the same claim, with `ToolOutputWritten` evidence. Unknown or ambiguous known sessions do not fall back to a sibling's process identity.
6. Generic policy snapshots eligible messages, exclusively prepares a bounded frozen batch with `InboxConsumer`, and offers actual content. Before any provider write, the final adapter validates the fence and durably calls `mark_issuing`. Admission/turn completion do not confirm delivery. Codex confirms only exact thread + batch correlation + frozen text in a native recorded user-message item; hook/tool output confirms only after successful flush. Receipt evidence must match the frozen claim consumer.
7. User cancel, approvals, input and connection exit remain native operations with priority over new internal offers. Cancellation is neither delivery evidence nor no-input evidence. Close retires only this controller and stops new internal work; it preserves uncertain claims and does not signal/cancel the shared backend or sibling roots. Reattachment cannot unlock an unresolved predecessor.

## Native deployment decision and evidence limits

sake's isolated installed-0.167.0 probe found managed daemon start ignores supplied service-level `-c` overrides, and its control socket speaks Unix WebSocket. The frame transport contract supports this. A discriminating follow-up established `thread/start.config` hooks + trusted state execute a real UserPromptSubmit hook without process hook flags or user config writes; its fixed loopback turn completed. Architecture therefore retains the official managed daemon and verified per-thread configuration overlays; the previously considered alternate listener is unnecessary on current evidence. Required configuration that cannot be mapped honestly to supported thread fields must fail explicitly. Do not ignore flags, write user config, or create a private/second backend.

Probe artifacts: [thread-hook summary](../../.agentx/.tmp/deliveries/codex-shared-runtime/native-service-probe/thread-hook-summary.json), [hook lifecycle summary](../../.agentx/.tmp/deliveries/codex-shared-runtime/native-service-probe/thread-hook-lifecycle-summary.json) and [connection summary](../../.agentx/.tmp/deliveries/codex-shared-runtime/native-service-probe/connection-summary.json). The lifecycle follow-up observed thread/start, resume and fork overlays executing UserPromptSubmit across three completed loopback fixture turns. The connection probe observed a second connection's active turn surviving the first connection's close with the same backend generation. These bounded native facts release service/bridge composition; they do not establish the production parent/child path or full unmodified outer-product support. Investigation and authoritative service detail belong to [native-service](./tasks/native-service.md) and [topology](../../.docs/codex-activation/topology.md), with independent acceptance in the owning integration Task.

A9.4 distinguishes acquisition from connected capability degradation. The current managed implementation accepts the observed `0.167.0` service profile; an unsupported version/transport before connection returns an explicit service failure. No compatible shared path for `0.155` is established, and a private child fallback would violate backend selection. Once a compatible shared connection exists, usable native traffic can remain available when internal observation/activation is unavailable, with autonomous input disabled and diagnostics retained. This conditional degradation does not require forwarding over an unknown transport. Native version probes and non-app-server direct stdio retain their separate dispatch.

### Native tool environment compatibility

The actual parent-child integration exposed a narrower mismatch than arbitrary thread environment reuse: native shell tools add proved execution/presentation markers and prepend the selected managed package's `codex-path`. These do not by themselves request another backend. The selected correction normalizes only those proved fields, redundant locale derivation and the exact leading helper path; all other user PATH components/order, backend inputs, configuration and OS-generation fences remain significant. The receipt may retain per-key value digests and report differing names; it must not log raw environment values.

Unknown environment additions, including arbitrary explicit thread shell values, remain conservative acquisition conflicts. No fixture-specific names or wildcard new-key acceptance are permitted. Session overlays still supply their tool environment, but that does not prove a child requesting acquisition with a different backend environment can reuse the service. Broader arbitrary-new-environment child reuse is unestablished; no new provenance protocol is required to resolve this observed parent-child failure.

Environment names referenced by effective native configuration remain material even when their names overlap otherwise normalizable metadata. This includes provider `env_key`, `env_vars`, `env_http_headers` and other known native environment-dependency fields; a previously absent dependency becoming present is also a change. The native-service owner retains dependency values in compatibility evidence or rejects an unsupported dependency boundary instead of silently discarding it. Service-owned implementation/detail is in [native-service](./tasks/native-service.md) and [topology](../../.docs/codex-activation/topology.md); independent reuse/conflict cases and the production rerun belong to lobo.

The implemented guard has two owners. Service acquisition reads the same supported home/system config and requirements bytes for fingerprints and explicit dependency discovery; those declared inputs retain presence/value compatibility, while client-owned AgentX dependencies fail explicitly. Thread preparation in [configuration.rs](../../src/integrations/codex/configuration.rs) checks merged CLI defaults and outer root config before hook preparation or native effects. Known model-provider, MCP and profile declarations referencing normalized inputs through `env_key`, `bearer_token_env_var`, `env_vars`, `env_http_headers` or explicit `env` names are rejected because backend value/provenance cannot be established there. It uses the service-owned pure predicate rather than copying the normalization list. Unknown unrelated config remains raw; no complete plugin/environment-dependency analysis or new service/request protocol is claimed. Focused cases and actual parent-child verification remain independent integration work.

## Independent verification seams

`AttachmentStore` exposes row/session/controller identity and retired-fence validation. `PendingInbox` exposes claims, phase, immutable window/content, medium and delivered cursor; re-opened isolated SQLite tests must challenge stale receipts, consumer contention and predecessor recovery. The two ledger traits expose typed ids and independent request directions without a real model. `ServiceRequest` supplies program, argv, env, canonical home and AgentX storage explicitly; native management uses canonical home as its cwd, while the bridge's session configuration retains per-session cwd. `NativeConnection` has bounded receive timeouts so fakes can permute responses/events/control and exercise EOF. Actual shared-backend, per-thread environment/hook and parent-child composition need real isolated native evidence. See [A1–A11 acceptance cases](../../.docs/codex-activation/acceptance.md).
