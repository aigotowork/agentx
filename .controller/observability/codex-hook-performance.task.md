# Codex hook critical path

## Implementation record

The user authorized implementation and kept performance experiments and load tests out of scope. The two proposed parallel AgentX launches returned `Busy` before starting; bele implemented inline. The [native Hook contract](../../src/service/codex_hook.rs), [command adapter](../../src/integrations/hooks/codex/client.rs), [mailbox preparation](../../src/messaging/service_store.rs) and [route projection](../../src/db/mailbox_routes.rs) own the implemented details. No installed binary or running user service is in scope.

- The Launcher generates the managed entry for ordinary Unix Codex PTY launches. The entry reuses the effective host environment, validates input before daemon contact, and uses the authenticated Ready capability to send one combined request. Shared app-server, Windows, legacy commands, SessionStart and compact stay on their existing paths. The launch generation also fences confirmation. A managed callback does not start an absent daemon; a compatible old Ready selects legacy logic before writing a request.
- Empty mail returns without taking a writer lock, loading hints or creating a token. Bounded reads use direct-recipient and broadcast routes once covered; historical fallback remains authoritative. Existing exact receipt and pagination consumers retain their contracts. The Hook receives formatted context and confirmation only, with a byte limit checked before an oversized claim can commit. No-op positions skip the update and separate retained record. Explicit local transcript reads can discover a late file using the bound session and captured Codex home.
- Multi-file status updates reuse one instance snapshot and send one ordinary observer hint per outer event commit. Individual events still drive subscription, collision and recovery rules. An asynchronous TCP executor and indexed subscription projection remain conditional follow-ups; endpoint authority and acceptable polling fallback are not established for all affected consumers.

## Verification

The isolated Linux native run passed five callback cases (one pre-existing opt-in process test ignored). It covers one-connection wire admission, old Ready fallback before Call, a stale generation with no Call, managed versus shared hook declarations, exact actor and no-op position behavior, empty/no-receipt and prepared/confirmed output, indexed history, rollback and reset. Another 48 affected compatibility, session, model-request, observer, receipt and transcript cases passed on the same test executable. These checks report structural and correctness properties, not latency percentiles or throughput.

The [real process case](../../tests/codex_hook_fast_path.py) passed against `target/telemetry-check/debug/agentx` with disposable daemons and DB: one socket and one IPC attempt for empty `PostToolUse`, zero for a provider subagent, two for nonempty output plus confirmation, and one for a subsequent empty poll. The missing dotenv selector never ran on this path; the first empty callbacks created no token, and the final mailbox cursor reached the one emitted event. This verifies AgentX's internal command and daemon end to end, with the command-declaration shape covered separately. It does not establish installed adoption, a live Codex launch run, or production latency. The completed scope includes workstreams 1A–3 and the bounded coalescing portion of 4; decoupling TCP wake and subscription fan-out from dispatch is deferred as separately conditional work.

The [proposal](../../.docs/proposals/codex-hook-critical-path.md) owns the target behavior and trade-offs. The [static audit](../../.docs/observability/codex-hook-latency.md) owns the source baseline.

Implementation order for the first candidate is **1A + 1B → 2**; 3 addresses history scaling and 4 addresses load amplification. The service composition owner owns the integration point, result taxonomy and compatibility decision. Before work, follow the affected [native service](../../src/service/AGENTS.md), [daemon](../../src/daemon/AGENTS.md), [messaging](../../src/messaging/AGENTS.md), [database](../../src/db/AGENTS.md) and [events](../../src/events/AGENTS.md) guides. Update the owning environment and runtime/notification usage contracts when their new behavior is verified.

Design walkthrough cases to preserve for later finite, isolated verification: (a) apply identical position and normal tool activity; (b) distinguish busy-before-send, application rejection, and missing reply after a possible commit; (c) kill the hook before stdout, after flush and before confirmation, and after confirmation; (d) preserve old claims across a daemon restart or participant replacement; (e) compare PTY hook delivery with shared app-server native delivery, including a concurrent listen; (f) resume/fork/compact when a transcript is absent and later appears. Preserve existing user state and running services. These are future correctness and structural checks, not a request to run a performance experiment now. Record which runtime, build and scope were actually verified before making timing or rollout claims.

Return paths: use legacy invocation for new launches if the managed environment/source contract diverges; select the compatible daemon route before the first write; disable new projection reads while retaining event history and outstanding receipts; keep notification changes separable from ingress and mailbox changes. Installed binaries, hook declarations in existing sessions and live daemon adoption are separate from an isolated candidate. Remaining uncertainties are timeout values within the provider budget; exact per-thread environment parity for shared hosting; historical index rebuild and invalidation cost; and which post-commit effects actually dominate time. None is used here as a numerical performance claim.
