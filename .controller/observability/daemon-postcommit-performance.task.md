# Daemon post-commit performance

The [proposal](../../.docs/proposals/daemon-postcommit-performance.md) owns target behavior, guards, and trade-offs. The prior [Codex hook work](codex-hook-performance.task.md#verification) delivers the managed Unix PTY call path and coalescing inside a commit; it does not establish deployed adoption or a production latency baseline. The user authorized this bounded implementation; it was delivered inline and verified in isolation.

## Implemented outcome and evidence

- The optional [observer worker](../../src/runtime/notify/observer_hints.rs) has one thread, a queue of up to 256 pending registration IDs and one second pending TTL. Ordinary hints can be coalesced or dropped without waiting; the existing Events reader polls and advances its durable read position. The daemon writer's temporary [invalidation hooks](../../src/db/post_commit.rs) cover registration/control and participant identity changes. Revocation is deliberately conservative for all pending hints in the scope; a failed transaction may lose a hint but cannot create one. Retirement and other consumers still wake synchronously. Bare TCP cannot authenticate a reused endpoint after connect has already started.
- The [candidate indexes](../../src/db/subscription_index.rs) keep event matching and request-watch state in the existing KV rows. Only currently compiled explicit singleton `--type` predicates without raw SQL or collision override are marked; other subscriptions remain eligible through General, and replay stays on the previous selector. Both selectors preserve the KV row order; target and due-range queries still run the original guards and transitions. The initial verified rollout used opt-in startup. [Current source](../../src/service/application.rs#L25) enables indexing by default; `AGENTX_INDEX_EVENT_SUBSCRIPTIONS=0` reverts selection independently of observer hints. Retained indexes need not be dropped to switch reads back.
- Retained native request detail and existing slow/failure diagnostics include [bounded phase attribution](../../src/observability/post_commit.rs) and per-request observer admission counts. No new log is written per event. Worker success/connect-failure/expiry totals are not exposed in this slice; exact loss is not inferable from admission counts. Retirement, business subscription effects and untimed parts of application time can still contribute to reply latency.

The isolated Linux build ran five focused cases, including a held sender, rollback, end/re-register, capacity and coalescing, ordered notification/reaction parity, fallback before effects, and actual SQLite `SEARCH` plans for type, target, and expiry. Another 94 related CLI/observer/subscription/registry regressions passed on the same executable. Three real native IPC acceptance cases passed against disposable in-process daemon listeners with both opt-ins enabled, covering reset/old-generation rejection, ambiguous mutation reply, and queued/running distinction. No installed executable, live daemon, load test, or production timing result is part of this evidence.

Keep maintenance ownership in [Events](../../src/events/AGENTS.md), [DB](../../src/db/AGENTS.md) and [native service](../../src/service/AGENTS.md). The rollout follow-up starts with a separately selected disposable scope or daemon artifact and does not infer adoption from these tests.

Continue beyond this Task by evidence, in this order:

- If legacy callback latency persists, distinguish existing sessions still emitting old commands from the optimized path before changing code again. For `SessionStart`/compact, first attribute frozen instructions, dynamic snapshots and transcript lookup; preserve receipt recheck and stdout confirmation. For shared app-server, establish per-thread effective environment and attachment parity first; for other Providers, model each payload, timeout and delivery medium before reuse.
- If TCP or observer eligibility remains expensive, choose the next wake kind only when endpoint revocation, fallback schedule and user-visible delivery impact are known. PTY/message delivery and LaunchWait are not automatically eligible. If observer SQL selection itself dominates, consider an exact Begin/End-driven in-memory mirror before moving any DB access to a worker.
- If business subscriptions still dominate after candidate selection, start a separate durable-effect design. Require committed event order, persisted processing progress, explicit replay/reconciliation and side-effect idempotence or an honest unknown outcome. Do not reuse the lossy observer hint executor.

Design uncertainties recorded here: current installed/live adoption and breakdown are unknown; existing SQL candidate order must be characterized before introducing another index scan order; the ABA window of bare TCP cannot prove endpoint identity; and old subscriptions' actual mix will determine how quickly typed candidate selection helps. Each uncertainty has a concrete fallback in the proposal, so planning is complete without asking for runtime experiments.
