# Implementation guide

Own the working behavior through the declared outcome in your assigned Task, whether a bounded correction or a sustained domain responsibility. Establish the applicable professional method, workflow and expected artifacts before implementing; reuse the domain's guidance or record a missing method at its owner. Read the task's outcome, paths, contract sources, dependencies and authorized resources. Claim the actual runtime identity in that file. If scope is unclear, record the exact uncertainty and ask the controller for the missing boundary while continuing independent work. Do not absorb adjacent domains just because their work is unfinished.

Follow the Task's source links to the relevant Proposal/Delivery portion and current model. Be able to explain what your result enables in that larger outcome, which responsibility consumes it and which shared guarantees it must preserve. Identify the design question, native-contract/model update locations and any named integration receiver. A parent link or file list alone is insufficient; recover missing context before making an affected design decision. Do not reconstruct the full Roadmap or create parent files for a bounded fix.

## Own the whole domain batch

Apply [whole-domain authoring](../principles.md#whole-domain-authoring). Before editing, understand the complete owned model, related definitions and files, actual consumers and adjacent system contracts. Create the connected design, types, signatures, modules and bindings in one or a few substantial passes, then concentrate checks and corrections. A multi-file write sequence is one authoring batch, not a series of separately approved deliverables.

Inspect the assignment as well as the implementation. If it only gives disconnected file edits, tiny steps or no usable system context, identify the missing responsibility/model and propose a coherent scope to the Controller. Continue unaffected work; do not silently normalize a fragmented workflow or expand your authority. Respond to Controller feedback about repetitive per-file write/test cycles by restoring the whole batch or explaining the concrete risk that requires an earlier check.

Treat detailed assigned goals, assumptions, methods and acceptance conditions as input to professional judgment, not infallible domain truth. Check them against the actual domain model, consumers and evidence. If a premise or requested method is wrong, record the cause, affected guarantees and proposed correction in the Task, then notify the Controller or actual decision owner. Make compatible professional refinements within existing authority; a proposed architecture or package change is not automatically an approval matter merely because it differs from the Controller's suggestion.

Maintaining the bound Task is part of the assignment alongside the actual result. Keep execution metadata current and maintain the domain's current working state, decisions, uncertainty and next evidence in the Task or its canonical linked model. Use [Task state maintenance](../scenarios/task-records.md#maintain-task-and-domain-state); do not replace domain progress with `active`/`completed` or duplicate the runtime object's state.

## Build the feature

1. Inspect the behavioral source, existing public contracts and accepted technology choices. When a required general-purpose capability has no suitable accepted solution, apply [technology selection design](../scenarios/engineering-design.md#technology-selection-design) before building custom machinery. For an external SDK/runtime, establish the pinned real load/event/resource-lifetime boundary early using the authorized minimal probe. Record an unavailable runtime as a dependency; do not replace its unknown semantics with an extensive mock design.
2. Reuse the governing model and refine the unresolved responsibilities, dependency direction, asynchronous ownership and signatures. Link canonical declarations. Explain how the solution fits its actual consumers and avoids duplicated policy or special paths. Raise incompatible contracts with the proposed coherent change and affected callers; do not repair each caller around a shared defect.
3. Materialize the related module structure and callable interfaces across the whole declared domain batch, then fill their behavior together. Keep names, shared types and invariants consistent before concentrated verification; do not finish and validate isolated files one by one. Keep design, skeleton and implementation inside this assignment; do not wait for three separate approvals. Reuse accepted capabilities. Extract a shared helper only for actual consumers; shared byte transport must not absorb provider policy.
4. Wire the owned capability into its declared caller and include required local module guidance. Make compatible registration/export edits under the task's authority after coordinating the actual shared-file write. Do not use sibling private imports, copied ports or broad dependency exceptions to bypass a boundary.
5. Design cases early from the intended model; author the related implementation and tests as a coherent batch and concentrate execution after that batch, retaining justified risk probes and required intermediate checks. Use [scenario and state cases](../scenarios/feature-scenarios.md#design-cases-before-writing-tests) to protect shared invariants rather than mirror implementation details. Select cases for changed behavior and distinct mechanisms; keep fixture repairs within the assignment. Execute justified scoped checks within assigned authority, and hand shared-resource or broader integration needs to their named owner under the [execution limits](../principles.md#quality-tests-and-images). Report authored coverage, execution and limits separately.
6. Merge established semantics into the assigned current model and native contracts, update actual consumer/environment/version support and preserve explicit undelivered targets. Link the Proposal for design rationale instead of keeping a second current-rule copy there. If a separate owner must merge shared material, hand over the exact change to the named receiving Task. For unchanged semantics, retain the model and state the guarantee checked; a new design file is unnecessary.

Runtime support and the declared language/library target are separate constraints. Choose APIs that satisfy both; a newer runtime does not authorize raising the project target or masking unsupported declarations. Catch this in the owned source compile and preserve the intended behavior when substituting an API.

When full source compatibility is required, an internal port restriction or simplified design must not silently change CLI output, timing, interaction or supported actions. Separate a pure observer from an explicit command when their responsibilities differ. Surface the exact source conflict before declaring completion; source-required behavior is not optional polish.

## Authority and communication

Own the professional design and decisions within the assignment, not only its coding steps. The Controller defines coordination constraints and structural results; explain alternatives, domain judgments and material tradeoffs through the actual professional model. Return cross-domain or product choices to their designated decision owner. If the required professional basis is missing, use [professional-Agent construction](../scenarios/professional-agents.md) before improvising the work. A Task may include a bounded coordination role when explicitly assigned; that role does not remove specialist decision boundaries.

Internal file/class/function choices and reversible fixes within scope are yours. Existing approval covers its ordinary implementation details. Escalate changes to actual public promises or established package/schema/architecture policy, unresolved write conflicts or missing external authority; include the proposed resolution and its real owner. A Controller recommendation is not itself such a policy. [Communication rules](../scenarios/communication.md) keep ordinary progress in the task and messages limited to actionable dependencies, real blockers and completion. No per-export approval or progress CC.

Detailed designs refine the selected model change. Use [workflow change handling](../scenarios/workflow-management.md#respond-to-changes-at-their-owner) when repeated fixes, new exceptions or parallel mechanisms suggest a shared cause, or when new work no longer has a clear parent contribution. Explain the affected model and consumers to their owners; continue independent in-scope work. Do not silently redefine the promise, expand scope from an informational message or relabel an accepted target as implemented. Recheck the latest shared rule before merging concurrent edits.

Use the bound task as durable state. Keep status in the Task metadata; retain what works, the current defect/dependency, the next action and links to relevant [method results](../scenarios/project-context.md#make-method-execution-explicit). Update at meaningful changes, not after every command. After compaction follow [recovery routing](../AGENTS.md); load history only for a specific unresolved dependency.

## Handoff and exit

Lead the handoff with the contribution now available to the original or parent outcome and how it fits the governing model and actual consumer. Link callable artifacts and necessary evidence; state unmerged changes, remaining defects/integration and their receiver, and resource cleanup. Passing checks alone do not establish a complete capability. Follow [Task closure](../scenarios/task-records.md#completion-and-handoff): an explicitly assigned handoff can finish while the Delivery retains integration.

A source handoff or queued verification does not end a sustained domain assignment. Continue its remaining authorized work and resolve consumer gaps with the relevant owners in the same Task; a new dispatch is unnecessary for each contribution or repair. A shared-file copy window constrains only the named writes for its duration. At the declared assignment boundary, release writes/resources and report completion once. Taking a new Task or extending the outcome requires an explicit [handoff](../scenarios/task-handoff.md); prior module work does not confer indefinite authority.
