# Task Handoff

For authorized delegation, prepare and bind a real [task record](./task-records.md) before assigning a new or existing worker, using the project backend's actual file-binding contract where available. A message alone is not the durable assignment. A deliberately assigned Delivery/coordinating record may carry bounded coordination context; ordinary professional work still needs its maintained Task. Use actual paths and current authority; an empty placeholder does not assign work. Choose the handoff wording for the situation rather than copying a fixed prompt.

Keep the assignment message focused on the outcome and its contribution to the larger result, the worker's role/professional entry, and the Task path. Link the project/role entry for recovery. Put the relevant shared model, consumer relationships, constraints and contracts in the Task or its direct links; do not substitute a file list, test selector or instruction to fix a local failure for that context.

For feature/design work, the Task must expose the selected Proposal change and Delivery portion when present, the original model and native contract, any detailed design question to resolve, and who updates which design/contract/model destination. Follow the default [planning decomposition](feature-planning.md#planning-levels) through source links; aggregation stays at its upstream owner. Link a separate receiving Task when shared model integration belongs elsewhere. The worker should be able to recover this from files alone; a link to a broad Roadmap or a message saying “update docs” does not assign that responsibility. Small direct changes can carry the same basis in their existing Task without creating parent files.

A handoff must let the domain owner reason about the complete local capability and its place in the system, with adjacent contracts and integration authority. It is not a request to write one file and wait for the next instruction. The receiving owner should challenge fragmented scope or missing context and propose the cohesive correction; the Controller must resolve that feedback. A usable contract handoff within a sustained assignment does not require closing/rebinding that owner. Apply [whole-domain authoring](../principles.md#whole-domain-authoring).

Apply [context, not control](../principles.md#context-not-control): separate actual user/authority commitments, observed facts, Controller hypotheses and open professional questions. Explain why the work matters and which system decision/result it enables; leave the expert to refine the domain problem, objectives, method, state model and evidence. Open discovery can start with a question and useful decision boundary rather than invented exact signatures or a predetermined answer.

Explicitly assign Task maintenance as part of the work: current understanding, professional state, decisions, unresolved conditions and meaningful results must remain recoverable. The receiving expert examines the assignment, corrects compatible professional assumptions with evidence and raises changed shared promises to their actual owner. Accepting a Task does not waive critical judgment. Controller feedback and expert challenges update the same Task; no separate objection report or approval round is required.

Before launch or reassignment, distinguish a suitable [professional profile](professional-agents.md#match-the-work-to-an-existing-capability), available method/tool prerequisites and an available runtime instance. If the professional basis is missing, commission its construction and keep only dependent work waiting. For a child Controller, also declare its bounded workflow, allowed delegation/resources and parent reporting boundary; preserve the original Task/Delivery relationships.

Confirm the actual returned identity and readiness, then record the current binding. A launch attempt does not prove that a worker is running. Direct the worker to [communication rules](./communication.md): ordinary progress stays in the task, while actionable dependencies, real blockers, and completion go to the relevant owner. Existing task authority covers routine implementation details; an informational message does not expand the assignment.

When moving an existing worker to a different assignment, first confirm the prior assignment is closed or durably handed off and its write/resource claims are released. Bind the new Task and restore its outcome, domain contracts, authority and remaining dependencies; prior context does not extend the new scope. Contributions and repairs within an ongoing assignment continue under its existing authority; they do not each require a new Task or dispatch. Follow the Controller's [context reuse criteria](../roles/controller.md#close-rotate-and-remember) instead of always replacing or always retaining workers.

Use the authorized tool's current help or messaging skill for syntax. Continue useful nonoverlapping work while the worker proceeds. The return handoff explains the contribution established, its fit with the shared model/consumer, and remaining integration before linking artifacts, evidence, updates and cleanup. The receiving owner applies [outcome acceptance](workflow-management.md#recover-and-close-the-outcome). A completion message triggers that judgment; it does not automatically establish Delivery acceptance.
