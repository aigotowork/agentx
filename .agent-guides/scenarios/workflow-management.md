# Design and maintain the professional workflow

Use when organizing delegated work, verification or a changed collaboration. The [Controller](../roles/controller.md) owns coordination authority; [feature planning](feature-planning.md) owns planned outcomes and records. Apply [whole-domain authoring](../principles.md#whole-domain-authoring). Reuse a sound workflow for bounded maintenance rather than replanning it.

## Choose the coordination needed

Start with one qualified domain owner for the complete capability, including design, related definitions/modules, behavior, consumer integration and ordinary repairs. Parallelize only when substantial independent contributions or genuine professional boundaries outweigh context transfer, shared-write and integration costs. Several files, layers, phases or available Agents are insufficient reasons to split work.

A Controller or child Controller must resolve actual cross-domain, dependency or resource decisions. Remove a level that merely relays progress or repeats acceptance. A qualified implementer can own planning and integration inside its responsibility; specialist decisions remain with their professional owner. Use [professional construction](professional-agents.md) for a real capability gap, not a new process or role label alone.

## Establish the collaboration model

Recover the original user outcome, selected scope, retained guarantees, current model and actual authority before adopting a Task list. Inherited plans are revisable. Keep one concise view in the existing Delivery/controller record: complete user path → domain contributions and shared contracts → actual consumers → integration responsibility. Link models rather than duplicating professional detail.

Use the affected objects, responsibilities and operations to explain dependencies: which fact, input or guarded result enables which consumer? A technical derivation chain does not imply one Agent, Task or acceptance round per layer. Keep implementation readiness separate from final acceptance; a usable contract can release consumers before provider behavior is finished. Stage order is not a universal execution barrier.

## Define what each result must accomplish

Before assignment, establish the contribution to the complete capability, governing model/contracts, real consumer and completion/integration responsibility. Supply [context, not control](../principles.md#context-not-control): mark real commitments/facts and their sources separately from Controller hypotheses, and let the professional owner refine domain goals, methods and acceptance evidence. An uncertain assignment may seek a usable decision rather than a preselected implementation. Put this in the existing Task or direct source links. Give owners the whole-system path and adjacent contracts needed for their judgments; a parent link or file list is insufficient.

Assign complete domain authoring batches: related designs, types, signatures, modules, bindings and documentation are created together, then checked and corrected coherently. A few writes imposed by tool limits do not create separate work items. Design, implementation and consumer repairs normally remain one sustained responsibility. A usable declaration handoff releases another owner without closing the provider assignment.

Define write scopes after responsibilities. Coordinate shared files for the actual overlap without reducing capability ownership to individual paths. A method, test selector, capture batch or changed file is an execution detail, not automatically a Task. The specialist owns professional choices and current-model maintenance within the assigned boundary.

## Keep the definition and execution facts distinct

| Fact | Canonical owner |
| --- | --- |
| Workflow and shared decisions | Existing Delivery/controller responsibility and dependency model |
| Work scope, execution status, blocker and evidence | Original Task/Delivery, maintained by the assigned owner |
| Domain work state and transitions | Professional owner's model, maintained in or linked from the Task; distinct from Task lifecycle and product/runtime state |
| Readiness | Derived from actual prerequisites, usable contracts and resource availability |
| Runtime identity and assignment | Actual backend plus controller binding to role/profile, responsibility and resources |
| Professional competence and prerequisites | Professional entry and available method/tool support |

Keep the binding sufficient to recover actual instance, assignment, delegation limits, writes/resources, last meaningful observation and next real condition. A launch is not readiness, listening is not availability, and a lost runtime may still hold resources. Reconcile before replacement. Apply the original Task/Delivery lifecycle; do not create a second state machine or mirrored status ledger. Partial contributions do not close a sustained assignment or automatically release its resources.

## Admit ready work and bound subcontrollers

Use [ready-work scheduling](../roles/controller.md#schedule-ready-work) with current usable contracts and resources. Release independent work without waiting for unrelated acceptance. Do not invent work to occupy capacity or a fixed sequence of waves.

A child Controller receives a genuinely bounded outcome needing coordination, its authority/delegation limits, shared contracts, resources and reporting boundary. It owns its internal workflow; the parent owns cross-domain composition. Do not duplicate dispatch or flatten all descendant detail into the parent. Actual backend authority bounds all delegation.

## Bound verification and integration

Choose implementation responsibilities and verification cadence separately. Complete a coherent authoring batch, then concentrate build, scenario execution and repairs with the named integration owner. Parallel contributions do not each need their own clean install, package, environment or acceptance round. Keep required scoped checks and early bounded probes for named uncertainties that could invalidate design. An independently useful release, destructive operation or material migration may require an intermediate gate; state the actual risk and exit condition.

Plan decisive cases from the intended contracts before execution. Integration exercises actual cooperating behavior, not just generated artifacts or locally passing parts. A domain owner checks its changed guarantees; an integration owner checks missing composition and required public package/user flows. Independence does not require repeating valid author checks or adding a reviewer to every contribution.

Reuse an owned integration workspace, dependency cache and fixture/tooling. Reset business state or create bounded subscopes for different generations, destructive cases or cross-version behavior. A clean external package install can test dependency closure; it is not a per-Task or per-fix ritual. Preserve failed evidence and update the existing workspace for affected repairs. Reuse means common tooling and controlled state, not sharing dirty business data between incompatible scenarios.

Freeze only inputs still read by an active build/run. Once a candidate contains the necessary immutable inputs, validating it does not by itself freeze subsequent source development. Protect actual live-source/shared-resource dependencies and release each restriction when its need ends. Keep deployment and live adoption under their own authority.

Consume the designated executor's evidence for its supported decision. Do not routinely replay tests, re-read logs, recalculate fingerprints or issue a second receipt. Capture required artifact/source identity at the actual build/release boundary. Reopen affected checks only for relevant changes, contradictions, missing evidence or an explicit requirement. Stop when the promised result has adequate evidence; retain unfulfilled integration with its owner.

## Respond to changes at their owner

Both sides maintain the work arrangement. Before dispatch the Controller checks for a complete domain responsibility, system context, adjacent contracts and integration authority. During actual work it notices repeated tiny write/test/approval loops or missing assembly through existing artifacts and actionable events. The implementer examines incoming scope, assumptions, prescribed methods and proposed acceptance, challenging fragmentation, missing context or unsound professional premises with evidence and a coherent alternative. A Task author's coordination authority does not make its technical claims true. The Controller disposes of the critique or routes a genuine commitment/authority change to its real owner; compatible professional corrections do not need a new approval. Controller feedback on execution and worker feedback on dispatch must both receive a disposition.

Resolve the cause with the responsible owner: merge fragments, restore the common model, remove an unnecessary gate or explain the real uncertainty/resource constraint. Continue unaffected work and preserve established results. Do not create a periodic report, reviewer, progress poll or approval round for this mutual correction. Use [collaboration effectiveness](collaboration-effectiveness.md) for a substantive workflow concern, not every bounded repair.

| Finding | Disposition |
| --- | --- |
| Bounded implementation/fixture defect | Original owner repairs the batch and verifies affected guarantees |
| Missing selected capability | Plan its coherent contribution within existing authority; interim unsupported behavior does not remove the promise |
| Shared contract/model defect or recurring exceptions | Affected professional owners diagnose and correct provider/consumer responsibilities together; pause affected patching, not unrelated work |
| Evidence gap | Select the observation needed for the actual promise; do not invent a new feature or exhaustive parameter matrix |
| Intentional out-of-scope rejection | Preserve meaning and support limits; no automatic backlog expansion |
| Changed goal or incompatible promise | Product/authority owner decides; reconcile affected assignments and contracts |
| Missing profession, tools or external authority | Record the exact prerequisite and owner; release independent work |
| Lost runtime or ownership conflict | Reconcile actual effects/resources before handoff or replacement; retain uncertainty |
| Unnecessary work | Cancel within authority, preserving established effects and settling resources |

For professional conflicts, state incompatible assumptions, retained guarantees and consumer impact. Domain owners resolve technical choices; orchestration alone does not grant architecture authority. Use [system diagnosis](systematic-troubleshooting.md) for unexplained repeated failures. Do not substitute retries, smaller repair tickets or another layer for a causal model. Record the resulting shared decision and affected dependencies in their original owners, without silently redefining acceptance.

## Recover and close the outcome

After interruption, recover the original goal, current capability/gap, governing model and assigned contribution before the latest queue or runtime facts. Consult relevant project entries and current summaries rather than reconstructing chronological messages. Old identities do not establish live authority.

Acceptance combines the professional owner's judgment of domain correctness with the receiving owner's judgment of system/consumer fit. One qualified authorized owner can make both judgments. Consume designated evidence rather than adding a Controller audit. Resolve actual missing composition, current-model updates and resource cleanup even when every local test passes.

An explicit source-only handoff can close while the receiving integration remains open; a sustained assignment continues across ordinary handoffs and repairs. Close the Delivery only when its complete promised capability is supported. Task counts, generated files and finished Agents do not establish that. Preserve actual platform/fixture/adoption limits and references to evidence.

Keep current outcome/gaps, direct responsibilities, shared decisions and actual resource constraints in the Controller record. Detailed tests, artifact versions and repair history remain in their Tasks. Report system capabilities and material choices rather than every leaf event. Retain reusable lessons at their method owner and end coordination work when there is no useful nonoverlapping action.
