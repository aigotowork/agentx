# 持续设计管理

让用户和 Agent 共同面对一个能阅读、指认和修改的产品模型：能找到某个行为、分清当前与计划、看到相关主体和结果，并提出具体修改意见。

本方法用于产品、应用、模块和包的持续设计管理。它连接已有的场景、契约、设计和证据，不要求迁移全部历史材料，也不要求每个模块画同样数量的图。Agent 从 [AGENTS.md](AGENTS.md)进入，按[工作循环](workflow.md)执行，按[视图合同](views.md)选择表达。

一个功能可以跨越多次方案和交付。[功能设计维护](workflow.md#maintain-a-features-current-design)保持其目的、场景、专业来源与当前支持可读；[变化定位](workflow.md#determine-the-affected-updates)说明怎样确定需要修改、复核或保留的表达。[便携例子](feature-example.md)展示报告导出的首次设计、取消变化、跨功能规则和简单能力的不同处理。

## 怎样阅读一个产品

| 用户问题 | 阅读入口 |
| --- | --- |
| 它帮我完成什么？ | 产品范围和完整场景地图 |
| 这些名词分别是什么？ | 领域主体、身份、关系和生命周期 |
| 各部分怎样分工？ | 模块职责与契约关系 |
| 真正运行时发生什么？ | 进程、连接、资源和生命周期 |
| 我要怎样使用？ | 命令/界面入口、输入、默认行为与可见结果 |
| 这一步内部怎样完成？ | 场景流程、调用时序、失败与恢复 |
| 哪些已经可用，准备怎样改变？ | 当前、目标、差异及其来源与证据 |

总览提供导航，专题视图提供细节。模块、进程、领域实体分别表达；同一主体在不同视图中保持可追踪的身份。阅读界面可以提供选择主体、切换当前/目标、定位场景和跳转依据等能力；Markdown 与 Mermaid 也可以承载一个完整的小型模型。

## 状态怎样表达

“已确认的方向”“源码已有实现”“通过某个场景验证”“当前安装可用”是不同事实。每项重要能力或关系分别说明设计决策及落地依据，注明范围、版本/源码基准和仍未验证的部分。未知保持可见，不以空白或绿色节点代替。

产品的当前模型持续更新；历史运行与固定发行证据保留原身份。目标变化应能说明增加、修改、替换或移除的关系，以及受到影响的使用场景。

## 怎样维护

从[工作循环](workflow.md#enter-at-the-current-question)选择起点：新设计从用户结果推导，现状重建沿实际场景核对，语义变化比较旧/新承诺，语义不变的修正沿用已有模型。领域文档解释含义与职责，原生契约直接供实现消费。

方案比较同一场景下的变化，设计细化原主题和声明，计划按结果、职责与契约依赖安排，Task 引用需要兑现的规则。实现后将成立的结论合回当前主题，链接原工作记录；目标、实际支持和历史证据分别保留。模型与源码冲突时先辨明原因，再修正相应来源。

工具从原文档和声明派生查询、索引与阅读视图，作者继续修改原材料。普通维护不需要另建登记模型、来源清单或检查包；无法提取的含义仍可在文档中阅读和讨论。

方法的效果以具体阅读任务判断：一个没有参与实施的人能否找到所问行为、区分当前与目标、解释关键结果并指出要修改的位置。文档齐全和图形渲染成功分别只是结构与呈现证据。
