# 从想法到可用产品的设计流程

这是一条有依赖、可回退的工作路径。从当前尚未解决的问题进入，复用有效的研究、场景和合同；原型和实现发现新问题时回到相应决定。步骤产物可以放在同一份现有设计、场景或任务记录中，不要求每一步建立文档或获得一次批准。[通用产品设计](../../scenarios/product-design.md)继续拥有跨专业工作循环和唯一场景作者源。

## 1. 确定用户到底要完成什么

选择主要使用者与实际情境，说明触发原因、当前做法、障碍和需要的结果。把宽泛诉求变成可检查的任务，例如“找出昨日失败的执行，确认失败步骤及其当时输入”，而不是“做一个运行管理页面”。管理者、执行者、作者可能关心不同层次，不因登录同一产品就视为同一种任务。

结合用户说明、已有材料和实际界面判断问题。分别标记已知事实、观察和假设。重设计时复现被拒绝的工作路径，确认主要障碍属于任务缺失、概念混乱、导航、状态、规模还是视觉；不要立即换一套组件。

**推进依据：** 能说明这次优先完成的工作、成功表现、暂不涉及的部分和最大不确定性。对象、前提或目标仍不清楚时，先查现有上下文，必要时询问决定性问题，同时推进不依赖回答的部分。[发现](../product-design/discovery.md)与[需求](../product-design/requirements.md)提供专业深度。

## 2. 还原主体、关系与能力边界

从任务提取业务主体，核对实际来源与公共合同。对影响任务的主体明确名称、身份、状态、生命周期、维护者，以及与其他主体的关系。区分设计与实例、当前与历史、能力声明与当前可用能力、过程状态与结果；不强制每个产品采用这些分类。

同时调查现有生态：哪一方已经拥有评论、执行、身份、资料、配置等能力？产品通过哪个公开接口组合？若某条关键工作依赖尚不存在的操作，提前标记缺口和可行方案。不要在界面里重造别人的业务，也不要为了兼容现有显示方式往核心模型随意加字段。

可以用“主体—身份/生命周期—关系—操作及 owner—界面所需信息”的小表或关系图承载判断。选择图时标明边的含义。核心语义需要改变，回到[领域与合同设计](../../scenarios/engineering-design.md)处理；纯视图聚合由适当的查询或呈现层承担。

**推进依据：** 优先任务涉及的对象都能被准确识别，关系与操作有事实来源；已知缺口不会在后面被假按钮或隐式数据拼接掩盖。

## 3. 选出完整工作路径，推导信息架构

为优先任务连接“入口 → 找到对象 → 理解/选择 → 操作或判断 → 结果/依据 → 下一步或返回”。包含会改变结果的前提、异常与中断，不必列出所有细小点击。沿用消费产品的场景记录，避免另建一份易漂移的页面流程。

把路径映射到集合、详情、工作区、编辑与关联入口。哪些对象值得全局导航，哪些应在上下文中出现，由跨对象任务、访问频率和关系决定。直接链接和返回路径同样需要设计。首页可以是待处理队列、最近工作或范围总览，不能从“管理台应有仪表盘”开始。

用路径检查导航：用户能否从任一实际入口辨认范围，能否在相关对象间移动并回来？一条路径在某处需要用户手工记住 ID 或切去查文档，通常表示关系入口或上下文尚未设计好。

**推进依据：** 一份可走通的导航草图，以及每个页面承担的用户问题。没有被优先任务使用的页面先说明必要性，否则不急于建设。

## 4. 研究参考产品，确定页面结构

选择解决相近问题的参考：对象复杂度、使用频率、任务种类或规模有可比之处即可，无需同一行业。实际观察一条完整任务，记录下列信息，区分亲自操作、截图观察和文档推断。

| 观察什么 | 要带回的设计判断 |
| --- | --- |
| 用户从哪里开始、怎样知道当前位置 | 导航与范围表达的机制 |
| 查找、选择后，主区发生什么变化 | 集合与详情如何维持上下文 |
| 操作位于哪里、完成后怎样反馈 | 动作所属对象和结果路径 |
| 哪些信息默认出现，哪些按需展开 | 当前决策所需的密度和层级 |
| 对象多、失败、离开后返回时怎样处理 | 规模、异常与连续性策略 |

将观察写成“适用原因—采用部分—需要调整—不采用部分”，不用搬运整套视觉外壳。无法访问参考产品时，可继续基于已有证据设计，但不能声称已验证其交互。

按[页面方法](page-design.md)安排每页的定向信息、主要判断、常用动作、支持资料和原始依据。只有存在关键结构分歧时才制作少量替代方案，用同一任务比较；不为展示工作量堆候选。

**推进依据：** 能解释每个主要区域服务哪一个判断、为何采用这种结构；参考样式与实际产品语义不冲突。

## 5. 用可操作原型暴露结构问题

先做能够回答当前问题的最小原型。导航不明时用连通骨架；密度或视觉不明时用真实渲染；执行与恢复不明时接一条有代表性的真实能力。避免直到全面实现后才第一次看到产品整体。

代表数据应覆盖主要对象、关系分支、常见状态、长名称与足够的集合数量。优先复用已授权且可用的真实来源；受限数据和模拟依赖应明确标记。受控夹具适合检查规模、错误与未完成能力，但不证明真实集成。不能把实际存在、用户要求接入的业务用自建示例替代后宣称完成。

操作原型完成一条主路径，检查返回、空状态和一项关键异常。此时同时确定基本视觉规则：排版层次、密度、选择/状态/动作表达、间距、共享控件及窄屏策略。结构与视觉需要一起在实际内容中评估。

**推进依据：** 原型足以评判当前主要假设，缺失能力被清楚区分；发现结构性障碍时先回到步骤 2–4，而非在错误结构上增加装饰。[原型方法](../product-design/prototyping.md)说明保真度与模拟范围。

## 6. 将页面承诺落到真实合同

在大规模实现前，对完整路径确认输入、读取范围、动作、输出和恢复。关键能力可行性在步骤 2 就调查；此处将已经选定的交互落到可开发合同。必要时提前实现一条端到端切片消除风险。

| 需要确认 | 接口与实现应能回答 |
| --- | --- |
| 数据 | 从谁读取，按什么身份/版本关联，范围与缺失怎样表示 |
| 操作 | 谁执行，什么前提有效，如何报告接受、进展与结果 |
| 依赖 | 外部数据/行为如何注入，真实服务与测试替身如何选择 |
| 寿命 | 视图、草稿、请求、连接和执行实例分别由谁保持和释放 |
| 恢复 | 离开、失败、冲突或结果未知后，原操作怎样查询和继续 |
| 组件 | 父层提供什么状态和数据，子层暴露什么事件和操作 |

前端组件可围绕输入、用户动作和外部依赖定义公开合同；领域 SDK 和服务负责各自行为。组合平台通过公开能力工作，不深入对方私有结构兜底。UI 未经支持的承诺要补能力或收缩当前交付，不能掩盖。

**推进依据：** 每项界面操作有实际承接方，主路径不存在“点了以后再说”的部分。合同细节由[组件设计](../webdevelopment/component-design.md)、[交互与状态](../webdevelopment/interaction-and-state.md)及原服务声明维护。

## 7. 按完整切片实施，必要时并行

先交付一条贯穿读取、交互、结果与返回的路径，再扩充同模型下的对象、状态和规模支持。任务按有界责任划分，不仅按“页面一、页面二”或“前端、后端”拆开后期待最后自然拼上。

需要子 Agent 时，先把共享上下文放在可引用的现有设计/任务入口：用户与优先任务、主体及关系、已选页面结构、公开合同、视觉规则、真实数据来源、各自写入范围、完成证据和已知限制。无需复制聊天历史；一名新 Agent 应能据此说明自己交付如何支持整体工作。

可独立的服务、界面区域或接入分别实施；依赖未确定的部分先澄清合同或安排必要的顺序。整体负责人维护主路径、共享规则与集成验证。各模块自测不能代替产品验收，也不要求小改动启动协作。

**推进依据：** 默认入口承接实际数据和能力，关键占位已完成；用户可以独立走完选定路径。尚未建设的能力按真实范围留待后续，不把按钮或静态视图算作实现。

## 8. 验证理解、操作与恢复

技术检查、页面观察、真实交互和用户理解分别取证。围绕改动选择必要检查，复用原有测试和场景；不为低影响修饰新建测试系统，也不重复运行无关的业务效果。

| 要验证的承诺 | 合适的检查 |
| --- | --- |
| 实现合同正确 | 针对变更的类型/构建和必要行为检查 |
| 页面层级和密度可读 | 代表内容下的实际渲染；宽/窄或文字放大后的主任务 |
| 任务完整 | 从真实入口查找、操作、查看结果、查证并返回 |
| 异常可理解可恢复 | 选定失败、冲突、离开/返回或未知结果情境 |
| 规模下能定位 | 明确范围的搜索/筛选/分页与上下文保留 |
| 用户能够理解 | 让代表使用者在尽量不提示路径的情况下完成任务，观察误解和停顿 |

没有实际用户参与，就记录为 Agent 走查，不写成用户验收。自动无溢出检查不能证明内容可读，截图不能证明状态保留，集成通过不能证明发现性。最终联调时稳定相关实现和数据来源，避免持续热更新让观察对象改变；修改后只重验受影响部分。

把问题定位为任务/概念、导航结构、关系表达、状态合同或视觉实现，再回对应阶段。记录观察、影响、决定及修正后的证据，不把主观喜好当作已证实的用户障碍。[评估方法](../product-design/evaluation.md)与[前端评审](../webdevelopment/review.md)提供更多选项。

**推进依据：** 承诺的路径和主要风险有与之匹配的证据；设计、实现、实际跑过和用户确认分别说明，不互相替代。

## 9. 收敛交付，并留下可继续工作的依据

让当前设计反映实际实现，标明仍未完成的能力、理由和下一项有价值的结果。保留必要场景和原始证据，让后续修改能回到同一上下文。重复出现的局部模式在多处真实使用后再提升为共享组件或通用规则，避免提前造大框架。

结束本轮的条件是选定任务得到可用结果、相关问题已有处理或清楚界定，而不是完整实现想象中的所有平台能力。交付说明给出可进入的位置、能完成的任务、实际验证与限制。后续从新增需求和使用证据出发演进，[功能规划](../../scenarios/feature-planning.md)拥有 roadmap 与阶段管理。

## 按工作大小裁切

| 情况 | 采用范围 |
| --- | --- |
| 新产品或整体结构遭到否定 | 从真实任务重新核对模型与路径，串联上述流程；已可靠的合同和事实继续复用 |
| 新增一个已有主体的任务 | 复用产品导航与模型，补该路径、页面状态、合同和验证 |
| 一个页面的信息层级或布局问题 | 从步骤 4–5 和页面方法进入，追踪相关任务即可；若发现模型问题再回溯 |
| 既有组件的局部视觉修正 | 使用原设计系统和受影响的渲染检查，无需创建对象地图或规划 |
| 小型只读工具 | 以“找到信息并作出判断”作为完整路径，不要求管理菜单、编辑器或首页 |

每个阶段都应减少一个真实不确定性。若产物不能帮助下一项决定、实现或验收，就缩减它。
