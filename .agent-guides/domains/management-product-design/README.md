# 管理型产品与工作台设计

一个好的管理界面，让人找到正确的对象，理解它与其他对象的关系，在当前条件下做出判断或操作，并看到结果。页面的价值来自这条工作路径：它减少查找、记忆、来回切换和误操作，让人能够掌握一套系统。

这套方法适用于管理台、开发者工作台、运行与诊断平台、设计与资源管理工具等多主体产品。单一表单、小型查看器可只采用相关页面方法；内容网站、营销页和消费型产品的其他问题回到[通用产品设计](../../scenarios/product-design.md)。只读分析工具也可以有价值，前提是完成真实的判断或调查任务。

## 先建立工作模型

在画页面之前，连接下面五件事。已有设计能回答的直接引用；缺失的才需要继续分析。

| 需要明确 | 要回答的问题 | 怎样影响界面 |
| --- | --- | --- |
| 用户任务 | 谁在什么情况下，要做什么判断或完成什么工作？ | 主入口、常用动作与完成条件 |
| 业务主体 | 操作围绕什么对象？怎样识别，谁维护，如何变化？ | 对象名称、列表、详情及生命周期 |
| 对象关系 | 什么包含、使用、生成或依赖什么？ | 分层浏览、上下文链接、对比或关系图 |
| 可用操作 | 当前对象和状态下，实际允许谁做什么？ | 动作位置、前提、反馈与恢复 |
| 结果与依据 | 如何知道发生了什么，依据何在，下一步是什么？ | 状态、历史、证据及回到原任务的路径 |

它们是设计时的判断维度，不是必须落库的五张表。界面可以投影多个服务的数据；领域规则和写入权仍由原来的能力负责。

## 核心理念

### 1. 让产品支持完整的工作

“查看列表”通常是手段。继续追问：用户找到对象后要比较、配置、执行、追查还是做决定？把进入、定位、理解、操作、结果与返回连接起来。只有统计数字、目录和详情，不能自动构成用户所需的管理能力。

同时保持承诺真实。若当前只有读取能力，就明确支持哪些调查和判断；把缺失操作列为设计或交付缺口。不要为了看起来完整，制造无后端支持的按钮或另造业务流程。

### 2. 先理清主体和关系，再组织页面

文件夹、接口返回值和注册项可以是数据来源，却未必是用户工作的主体。一个入口可能包含多个对象；一个对象也可能聚合多个来源。依据用户如何查找、比较和操作来确定全局入口，在上下文中展示局部主体。

每个概念都应有可找到的表达位置，但不要求每个类型都有一级导航。只在一次运行中有意义的参与者，可以属于那次运行；需要跨运行查找的资源，才可能需要自己的集合入口。元信息应完整可达，默认优先展示当前决策所需部分。

### 3. 信息层级服务于判断

用户先需要知道“当前看谁、处在什么状态、能做什么”，再需要细节、关系和原始依据。让关键信息在同一视野内可比较；用逐层展开处理次要复杂度。密度来自有意义的分组、对齐和选择，不靠缩小字号，也不靠把每项事实装进一个大卡片。

标签、层级、位置和动作反馈共同解释产品。必要的规则、操作后果、空状态引导和恢复说明应保留；泛泛的口号不能修补无法理解的页面结构。

### 4. 界面表达本身会作出事实判断

编号暗示顺序，连线暗示关系，颜色暗示状态，总数暗示范围，按钮暗示可执行能力。每一种表达都必须与真实语义一致。互斥分支不能排成一条必经路线；一页已加载记录不能称为全量；“请求已接收”不能显示为“任务已成功”。

用稳定身份和正确版本维持关联，业务名称帮助辨认，技术身份在需要时可查看、复制。不要根据同名、当前行号或“最近一次”猜测对象。

### 5. 操作和上下文有自己的寿命

用户切页并不一定要结束任务。列表筛选、编辑草稿、运行实例、待确认请求和历史资料可能具有不同寿命。设计时决定何时保存、保留、释放或失效，以及返回时看到什么。不能让组件卸载替代这些产品决定。

历史与当前也要分清：历史使用当时的定义和资料，当前界面可以链接到最新设计，但不能把最新内容冒充过去现场。连接消失后，已留存内容的读取能力应按实际合同继续成立。

### 6. 参考成熟产品时研究它如何解决问题

观察一个完整任务：它怎样让人找到对象，在哪里提供动作，如何展开细节，操作后如何反馈，离开后如何返回。记录这些安排解决的具体困难，再判断自己的主体、规模与使用频率是否相同。

导航栏、页签或配色可以相似，背后的任务不同就可能需要不同结构。真正可借鉴的是组织信息与维持工作连续性的办法。

### 7. 实现和验证围绕同一条路径

产品设计、领域合同和实现并非互不相干的工序。页面承诺某个动作后，就要知道哪个能力承担它、需要什么输入、结果何时成立、失败怎样恢复。跨端整合复用已有业务能力，界面承担选择、组合与呈现。

有可点击原型、代码通过测试、实际链路跑通、用户能够理解，是不同层次的证据。完成度按原任务判断；组件可用、截图好看或检查全绿都不能单独代表产品好用。

## 常见症状与应该回到的问题

| 看到的症状 | 优先检查 |
| --- | --- |
| 满屏目录和字段，管理者不知道能做什么 | 用户任务是否明确；主体、操作与结果是否接成完整路径 |
| 换了配色和卡片，使用仍然困难 | 结构问题是否被当成视觉问题处理 |
| 顶部堆满解释性文字 | 名称、分组、动作与反馈是否能表达真实含义 |
| 几个对象时好看，数量增加后无法定位 | 搜索、筛选、排序、范围与返回上下文是否设计过 |
| 状态都叫“成功”，出了问题无从排查 | 过程、业务结果、检查结果、资料完整性是否混淆 |
| 每个页面都能打开，任务仍然做不完 | 跨页身份、草稿、待定操作和恢复是否连续 |
| 设计稿完整，实际页面空白或按钮无效 | 实际数据、能力与操作合同是否支持界面承诺 |

先修正产生症状的模型或路径，再调整布局和视觉。采用[流程](workflow.md)时按当前缺口进入，不必从头重做已经可靠的设计。
