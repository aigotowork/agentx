# 怎样设计一个真正可用的页面

Before page design or review, read [product and interface design requirements](../../scenarios/interface-design.md). Their layout, density, disclosure, visual language and semantic implementation constraints apply here, including narrow screens. Reuse them when already read.

先选一项真实任务和代表数据。写清“用户来到这里，是为了对什么作出什么判断或操作”。页面可以兼顾相关任务，但不能以“展示这个模块所有内容”代替职责。新产品的整体推导使用[设计流程](workflow.md)，本篇解决具体页面及相邻页面怎样承接工作。

## 1. 明确页面承担的工作

在现有设计中用一小段话或线框标注下面的信息，不必新建模板文件。

| 问题 | 设计结果 |
| --- | --- |
| 从哪里来？能否直接打开？ | 列表、搜索、外部链接等入口，及每种入口的定向信息 |
| 当前范围和主体是什么？ | 项目、对象、版本、时间范围、筛选；只保留影响任务的维度 |
| 需要做什么判断？ | 必须同时可见的事实、关系、差异或状态 |
| 常用动作是什么？ | 对当前主体生效的动作、可用条件与结果 |
| 怎么知道完成、失败或还不确定？ | 明确反馈、依据、可行恢复 |
| 接下来或返回哪里？ | 相关主体入口、原列表上下文及草稿/运行保留方式 |

如果回答依赖“先让用户读一大段说明”，检查名称、分组和任务是否正确。遇到专业规则或重要后果，则在相关控件旁提供必要说明，不把自解释界面误解成不许写文字。

## 2. 用导航区分工作范围

全局导航表达稳定的工作入口。跨对象重复查找、具有独立任务和生命周期的集合，适合作为候选入口；只属于当前对象的详情，留在局部。入口名称来自用户领域，不来自后端服务名或目录名。

| 用户正在做什么 | 合适的承载方式 | 需要保持 |
| --- | --- | --- |
| 在很多对象中查找、排序或比较 | 对象集合页，配搜索/筛选/表格或其他合适集合表达 | 当前范围、排序、选择与返回位置 |
| 持续处理一个对象并查看相关资料 | 详情页或工作区 | 主体身份、状态、常用动作与关系入口 |
| 浏览同一主体的不同侧面 | 局部页签或分区 | 同一个主体；同时比较的内容不拆到互斥页签 |
| 短暂查看关联对象后继续原工作 | 当前工作区内的检查器、浮层或抽屉；明显不同的任务再使用可返回子页 | 原任务、选择和焦点；窄屏优先局部分层，不因宽度自动拆屏 |
| 做一项短暂、范围明确的确认或输入 | 对话框 | 清楚的提交/取消和结束后的焦点位置 |
| 完成较长的编辑或复杂配置 | 可恢复的编辑页面/工作区 | 草稿、验证、冲突与退出语义 |

不要让同一套页签同时改变主体、工作模式和全局范围。多层导航应有不同职责；面包屑表达实际层级或来路，关联关系使用明确链接。深链直接进入时，也能识别对象、版本与可用上层入口。详细合同见[导航与恢复](../webdevelopment/navigation-and-recovery.md)。

首页不是必须存在的仪表盘。如果用户通常从队列开始，就让队列成为入口。需要总览时，让它回答“当前管理什么、哪里需要处理、从哪里继续”，每个摘要能落到对应范围的对象。没有决策用途的计数和图表不占首屏。

## 3. 安排信息层级与空间

按当前任务分配注意力，而不是把数据的重要性永久排成一张表。相同字段在不同工作中可以处于不同层级。

| 层级 | 常见内容 | 表达方式 |
| --- | --- | --- |
| 定向与行动 | 当前对象、所属范围、关键状态、主动作 | 稳定标题区或工作区工具栏 |
| 当前判断 | 关键字段、进度、关系、差异、必要前提 | 主区域中可一起阅读和比较的结构 |
| 支持判断 | 细项、关联对象、历史、辅助操作 | 有摘要的分区、选中后的检查器、合适页签 |
| 查证与诊断 | 原始数据、技术标识、协议记录、完整元信息 | 明确可达的详情、展开或下载入口 |

逐层展开不能隐藏用户决定是否执行所必需的信息，也不能把异常埋到默认关闭的“更多”里。收起时保留异常提示或有意义摘要。默认展示业务标题和上下文；技术 ID、版本等保持可查可复制，排查任务确有需要时再提升其优先级。

先决定哪些内容必须同时看见，再建立单栏、列表详情、编辑预览或多区域工作区的 layout 骨架，之后实现功能组件。必须提高一屏内的信息与操作效率：主任务上下文及高频操作共存，二三级动作在局部层级可达，并以同任务、同数据、同 viewport 下的信息及操作数量和到达步骤评估。明确谁滚动、谁保持可见，避免每个小区域都成为难以操作的滚动容器。卡片适合少量异质摘要或独立选择，不适合把大量同结构记录逐项放大。

## 4. 选择不会误导的表达

基础图表选择见[工具界面](../webdevelopment/tool-interfaces.md)。选定表达后，再检查它隐含的事实：

| 表达 | 隐含含义 | 必须核对 |
| --- | --- | --- |
| 编号列表、步骤条 | 有先后、进度或必经顺序 | 是否确有次序；作者排列与实际执行能否分清 |
| 树和缩进 | 包含或上下级 | 是否实际为多对多关系；同一对象的多处引用如何识别 |
| 有向图 | 边有方向和语义 | 互斥、并行、汇合、回路是否保留，遗漏节点是否说明 |
| 时间线 | 事件的时间关系 | 时间来源、未知顺序、并发及未收到的事件是否区分 |
| 统计或状态分布 | 相同口径的对象集合 | 范围、单位、过滤、是否全量，状态是否重叠 |
| 关联与比较 | 同一身份或有依据的对应关系 | 来源、版本、比较基线；同名是否只是巧合 |

管理与工具页面优先通过可视化表达比较、趋势、分布、进度和关系，避免用解释段落让用户自行重建模型；精确查询和逐项操作使用对齐表格。图很大时按当前问题裁切、分层或聚焦邻接关系，并提供查找和可读替代视图，不把全部节点塞进一张缩略图，也不添加无决策用途的装饰图。颜色、位置和形状辅助理解，关键含义也要有可访问名称或简明标签。

## 5. 让操作有明确后果和反馈

把高频、对当前对象生效的动作放在其上下文中；集合批量操作先显示选择范围，局部动作靠近其对象。主动作按状态变化，不必在每个区域都放一个醒目的按钮。

对会改变数据或运行状态的操作，逐项确定：目标与范围、可用前提、输入、执行方、等待期间仍可做什么、如何确认结果、失败或未知时如何恢复。沿用实际服务合同，不能从 UI 的超时自行推断业务失败或取消。

| 当前事实 | 页面应表达 | 避免的误判 |
| --- | --- | --- |
| 尚未创建/开始 | 当前已有内容和真实的首次入口 | 默认报“未连接”或全页空白 |
| 正在读取某一区域 | 局部等待，保留仍有效的上下文 | 一次刷新清空整个工作台 |
| 范围内确实没有数据 | 空集含义和适用的下一步 | 虚构样例、数量或可用能力 |
| 搜索无结果 | 当前条件，可调整/清除的入口 | 当作首次使用 |
| 请求已接收，任务仍执行 | 当前进展和可用操作 | 显示最终成功 |
| 回复丢失，效果无法确认 | 原操作身份、实际可用的查询/恢复途径 | 自动重发或给出未经合同支持的“重试” |
| 读取失败或资料不完整 | 受影响的部分、已知事实和缺口 | 把错误转换成空数据，把完成转换成通过 |
| 草稿与保存版本冲突 | 保留草稿、当前版本及明确处理入口 | 静默覆盖或刷新丢失输入 |

只设计实际可能的状态，不铺满所有状态组合。用户尚未请求的危险动作也不应为了“演示操作闭环”擅自执行。详细状态与效果所有权交给[交互方法](../webdevelopment/interaction-and-state.md)。

## 6. 为增长和返回使用设计

使用足够暴露问题的代表数量和内容：长标题、重复名称、多层关系、多种状态与缺项。对象增长后，搜索、筛选、排序和分页需要清楚的作用范围。客户端只搜索已载入的一部分时，应明示范围或采用真正覆盖目标集合的查询；不要让用户误以为不存在其他对象。

跨页保留与任务相关的筛选、选中项、位置和草稿。对象被删除、访问能力消失或版本变化时显示具体变化，不能悄悄选择另一个对象。返回运行时，应恢复原实例或准确说明它已结束；查看旧步骤不能触发执行。

提前区分页面视图与长期工作：连接、编辑内容、待定请求、执行器、留存结果分别由谁保管。相关服务或状态可以高于视图层存活，但无需为了一个只读弹窗建立全局状态框架。实现的范围取决于任务寿命。

## 7. 形成一致、可操作的视觉语言

明确标题、正文、辅助信息和诊断信息的排版层级，保持列对齐、间距与分隔规则，主体突出、简洁清晰，倾向浅色系。颜色区分选择、动作和状态，同一个含义跨页面一致。共享 token 和基础控件；业务局部差异也必须用语义化 CSS 类与变量承载，不能留下自由数值或组装层样式细节。具体实现沿用[设计系统](../webdevelopment/design-system.md#token-and-theme-design)。

用真实长度的内容评估可读性。缩小宽度、放大文字时，先用布局适配和浮层/抽屉保留当前任务、主体与主操作，比较任务保留必要的共同上下文；只有明显不同的任务才切换页面。不能只隐藏一栏或默认拆成前后屏来声称完成响应式适配。

检查语义结构、键盘操作、可见焦点、焦点返回、选中态、对比及不依赖悬停的关键动作。图形需要可读替代和可操作的选择入口。WCAG 的 reflow 具有二维内容例外；处理主任务连续性和例外范围，不能把“没有横向溢出”当作可访问性或可用性的充分证据。具体实现沿用[Web 指导](../webdevelopment/implementation.md#accessible-and-responsive-implementation)。

## 8. 在实际页面上追踪一条任务

拿同一任务和同一批代表数据检查：能否确定当前范围、找到对象、解释关系、选择正确操作、理解结果、进入依据、再回到工作。另选一个主要失败或中断情境，检查它是否仍然成立。

观察真实渲染：检查器是否有可读尺寸，主动作是否可达，焦点是否正确，长内容是否挤走重要部分。再实际操作导航与恢复。截图可以证明画面，不能证明离开后请求仍可查询；类型与构建通过不能证明用户看懂。

若发现问题，记录“场景—实际表现—对任务的影响—对应设计决定—修正后的复查”。分清结构、关系语义、状态合同和视觉问题，修改其真正归属。详细证据选择见[前端评审](../webdevelopment/review.md)。
