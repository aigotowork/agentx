# Renderer and release checks

Use before promising a rendering feature, implementing integration or publishing. The consumer's native content, media, component and release contracts own exact support. Reusable editorial guidance does not implement those capabilities.

## Discover the actual publishing path

Start at the consumer's content/module entry and follow native definitions only as far as the selected artifact requires. If local bindings are absent, record the actual source of each consequential fact in the existing Task. Do not substitute the original author's repository layout.

| Question | Inspect | Consequence |
| --- | --- | --- |
| Which source is selected? | CMS/file configuration and source composition | A new file may be valid yet absent from the site |
| What identifies published content? | Slug, source partitions, locale, references, state and URL contracts | Preserve existing content and identity across source changes |
| What body syntax is supported? | Actual parser/compiler and component map | Markdown, trusted MDX and editor JSON can have different capabilities |
| What can execute? | Import allowlist, typed blocks, trusted-source rules and sanitizer | A JSX example is not permission for arbitrary CMS execution |
| How are figures delivered? | Mermaid version/transform, SVG/image paths and failure behavior | A fence can remain code until a renderer/export exists |
| How are audio/video/assets served? | Source schema, upload/storage/public serving and playback | Image support alone says nothing about video/audio |
| Can work be embedded? | Allowed origins/sources, parameters, iframe policy and client boundary | Verify resizing, focus, mobile input, launch and fallback |
| How is content projected? | Search, text/Markdown adapters, summaries and discovery policy | A visual or executable body may not have complete machine text |
| How is it released and refreshed? | Preview/publication workflow, build/check matrix and deployment owner | A local draft, preview and live publication are different states |

Separate observed support from proposed integration. An unavailable capability leaves a named gap. It does not justify silently changing the whole content source, enabling indexing, weakening a safety check or removing existing CMS content.

## Choose a feasible route

| Need | Candidate route | Check before promising completion |
| --- | --- | --- |
| Prose, code, tables and images | Existing supported content workflow | Selected source, schema and actual compilation/rendering |
| Editable model with static figure | Verified renderer export in a supported media path | Source/export relation, readable output and textual interpretation |
| Dynamic diagram or experiment | Trusted component or finite typed CMS extension | Model, allowed inputs, accessibility, failure and projections |
| Dedicated work | Inline, independently hosted, approved embed or full-page/download route | Fixed version, host policy, size/input, ownership and fallback |
| Video, loop or audio | Supported hosted media and playback renderer | Format/encoding, controls, captions/alternatives and actual delivery |

Keep the current source when it meets the artifact's needs. If source composition must change, model partitions and existing identity first. A CMS extension needs its actual finite block/parameter contract, author controls, rendering and projection. Do not paste arbitrary scripts into content to bypass missing support. A dedicated project can meet an ambitious content goal without rebuilding every publication path.

## Keep human access and machine projections distinct

Supply a route to the central relationship when the main medium is unavailable: static exported model, keyframes, event table, representative inputs/outputs, transcript or independent launch where appropriate. Describe missing exploration honestly.

Then check actual search/text/Markdown behavior separately. Unknown JSX, expressions, embeds or video may need an adapter, summary or explicitly unsupported alternate under the consumer's schema. Nearby prose does not automatically make a body projection complete. Do not invent frontmatter fields or copy a different project's discovery values. If the reduced capability is unacceptable, use supported static content or implement and verify the adapter.

Ensure diagrams, controls, captions, alt text, source metadata and machine representations refer to the same relevant model and version. Search should not promise unavailable content. A human-readable fallback does not override the compiler's capability judgment.

## Verify the selected deliverable

| Deliverable/change | Appropriate checks | What remains separate |
| --- | --- | --- |
| Planning only | Brief completeness, source resolution, model consistency and feasible delivery | No claim of finished media, runtime or publication |
| Text/static draft | Facts, links, heading/identity metadata and relevant content compiler | Build success does not validate the thesis |
| Diagram/chart export | Actual version rendering, units/semantics, labels, theme/size and alternative | Rendering does not prove the model |
| Component/runnable work | Teaching cases, production build/hydration, meaningful reader/browser path and cleanup | A simulator does not validate production services |
| Time-based media | Actual playback, legibility, timing, controls, captions, audio modes and unavailable state | Storyboard/source inventory does not establish delivery |
| Published update | Actual selected source, public route/state, URL/locale preservation and affected representations | Preview success is not a live receipt |

Use the consumer's actual check matrix and UI/accessibility methods. For renderer or layout work, select the applicable [Web development](../../webdevelopment/AGENTS.md) and [interface design](../../../scenarios/interface-design.md) methods. Capture or interpret UI evidence under [observable feedback](../../../scenarios/observable-feedback.md). Publication operations use the actual authorized workflow and [release/recovery method](../../../scenarios/release-and-recovery.md) when relevant; these links add no authority or mandatory approval.

Set runtime budgets from the work's needs and the host baseline. Measure chosen dependencies and startup in their real path. Keep expensive optional execution local to the artifact, clean up observers/animation/resources, and preserve failure access. Isolate validation resources; do not reset normal user data or exercise paid services merely to check content.

Record actual commands/procedures, source/artifact version, outcomes, unresolved failures and scope in the existing Task. Distinguish authored cases, executed checks, static review and unverified behavior. Stop after required checks pass unless changed relevant inputs or unresolved failures justify another run. Publication requires the selected artifact and actual host checks, while learning or operational improvement remains a separate evidence claim.
