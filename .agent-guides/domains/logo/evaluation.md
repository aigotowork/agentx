# Evaluation and delivery

Use when checking a candidate, deciding whether an iteration is sufficient, preparing production assets or evaluating this method. Select checks that answer the actual brief. There is no universal “professional logo score.” Keep hard requirements, craft judgments, preferences and untested hypotheses distinct.

## Four coverage checks

1. **Task coverage:** connect every material user requirement to an artifact/decision, evidence or explicit remaining gap. Exclusions need a reason; deferred requirements remain incomplete.
2. **Method continuity:** the current action has its needed inputs and produces something the next action can use. Missing source identity cannot be repaired by a beautiful board.
3. **Exploration coverage:** identify which concept regions were examined, which were deliberately left open and whether candidates differ beyond finish. No fixed candidate count proves diversity or exhausts creativity.
4. **Capability coverage:** each required operation has an available tool, a legitimate manual path or an acknowledged dependency. A proposed adapter is not an available capability.

Use the minimal [coverage record](collaboration/records.md). These are checks within the current scope, not mandatory extra meetings or user approval gates.

## Evaluate at the right stage

| Stage | Useful criteria | Evidence and limit |
| --- | --- | --- |
| Concept exploration | Connection to brief, distinct propositions, plausible formal expression, range requested by user | Design reasoning and user comparison; not proof of market recognition |
| Craft refinement | Contour, anatomy, letter structure, spacing, hierarchy, optical balance and coherent expression | Source inspection and actual visual review where allowed; parsing alone is insufficient |
| Material development | Consistent light, surface, scale, source fidelity and intentional role | Relevant rendering and context; an effect mockup is not a fabrication master |
| Identity system | Shared recognition cues, relationship of assets, actual needed sizes and contexts | Real variant files and use cases; not a requirement to create every possible variant |
| Production delivery | Editability, dependencies, naming, formats, source provenance and intended consumer | Actual exports and checks in the relevant runtime/process |

## Technical checks

Check the actual format and delivery path. For SVG, relevant checks include parseability, viewBox/bounds, definition IDs, external resources, clipping/masks, real transparency, text/font dependencies and render compatibility. Rendering should not silently omit unsupported constructs. Do not convert an image wrapper into a claimed vector source.

For raster, check dimensions, alpha when required, color intent, cropping and edge behavior at intended sizes. For 3D or material work, preserve the source or state what is editable and what exists only as an image. For type, verify exact spelling and needed scripts, dependencies and delivery license conditions.

A renderer can detect errors or create size previews; it cannot certify that a silhouette is distinctive or the kerning is good. A second renderer is useful when export/runtime differences matter, not a mandatory repeated expense for every draft. Use actual output checks and the appropriate production path.

## Visual and audience checks

Where review is allowed, evaluate the intended reading and main cue before secondary details. Check figure/ground, joins, hierarchy, word rhythm, optical weight, relevant backgrounds and size behavior. Compare near alternatives when distinctiveness is a concern. Record observations and consequences rather than “looks professional.”

User preference, designer judgment and audience recognition answer different questions. If recognition or interpretation matters enough to test, use an unprimed task with representative people and the actual artifact: ask what they see before explaining the intended metaphor. Keep conditions and exact responses. A few responses can reveal problems; they do not establish universal memorability or preference.

When image inspection is disallowed, mark visual judgments as not performed and rely only on user feedback actually received. Do not secretly read images to satisfy a methodological checkpoint. A user's selection can settle their requested exploration while leaving technical or visual-production claims unverified.

## Accessibility and cultural use

Logo/logotype text has a specific exception under WCAG contrast-minimum; do not impose an invented 4.5:1 logo requirement. The surrounding interface, interactive behavior, focus indication, accessible names and applicable non-text contrast obligations still need evaluation in context. Review actual visibility and offer appropriate variants rather than using the exception to justify avoidable invisibility. See [sources](research/sources.md) for the scoped W3C reference.

Review relevant cultural interpretations and major existing similarities when needed. A reference search or image similarity tool can flag candidates for review; it cannot provide legal trademark clearance. Verify adopted material and font permissions at the point of use. Do not turn every rough sketch into a legal review project or claim clearance without the relevant work.

## Deliver only what exists

A concept delivery may consist of contact sheets, editable drafts, short propositions and a next decision. Production delivery follows the actual brief and may include:

- Editable master sources with readable versions and resource/font requirements.
- Needed primary, lockup, compact, single-color or expressive assets, with derivation relationships.
- Actual export files for web, print, fabrication or another agreed medium.
- Clear-space and minimum-use guidance justified by the chosen design and process, not borrowed ratios.
- Color/type information, source provenance, permitted uses and remaining dependencies.
- A short handoff naming intended consumers, verified uses and material limitations.

Do not dump unused formats or fabricate a brand manual for a one-off concept. Do not reduce a rich primary identity to a favicon requirement; derive an appropriate compact asset when the application needs it.

## Integrate through the consumer's asset owner

Locate the consuming project's canonical identity source, asset entry, export commands and actual application references. Read those contracts before changing production assets. Establish whether the source supports the chosen artwork or represents only the current configured mark; a hardcoded generator is not a general asset registry.

Edit the canonical source, run its declared exports and the checks affected by the actual change, and connect the resulting files to their consumers. When generated files exist, preserve that ownership rather than independently redrawing the outputs. If there is no exporter, deliver the agreed source and exports with an explicit derivation and a usable editing path; a new export platform is not required.

Exploratory candidates stay in the project's existing design/task area until adoption is within the authorized scope. Keep prior assets and unrelated edits intact. Record which source/version, exports and uses were checked and what remains unverified. Acceptance of a design does not itself authorize publishing or deployment.

## Test this methodology itself

The current method is a reasoned synthesis, not a validated guarantee. Evaluate it on actual bounded requests before claiming improved quality or reduced effort. Compare with prior practice on the same brief and appropriate model/tool context when a comparison is useful; avoid inventing participants or scores.

| Case | Desired behavior | Evidence to retain |
| --- | --- | --- |
| Sector given, style open | Several defensible territories; no sector-driven style lock | Brief assumptions, candidate differences and user reaction |
| Explicit ornate/metal animal | Anatomy, art direction and material survive the workflow | Source and expression relationship; craft failures found |
| Approved form needs refinement | Retained cue and purposeful changes | Before/after versions and scoped feedback |
| References with mixed preferences | Likes attach to traits rather than entire images | Reference attribution and subsequent design decision |
| User cannot name the dissatisfaction | Relevant accessible choices, preserved raw statement and a discriminating next-round plan | Submitted option targets, interpretation and actual subsequent changes |
| Feedback changes during an activity | Fixed execution inputs, preserved later opinion and result attribution | Initiating plan/input snapshot, later feedback and the next-round basis |
| Interruption, unknown save or partial result | Honest state, preserved usable work and legitimate recovery | Actual persistence/operation behavior and restored comparison context |
| Workbench moves between chat, canvas and narrow layout | Shared targets and supported drafts survive; user can correct the agent's interpretation | One complete interaction path with keyboard/touch/focus checks where implemented |
| No image inspection | Artifacts generated without tool-policy conflict or false visual claims | Actual tools used and stated validation limits |
| Tool or reference unavailable | Honest capability limit with useful independent progress | Missing dependency and produced work |
| Production update | Canonical source, exports and actual use stay aligned | Integration checks and artifact lineage |

Assess direction diversity, translation of feedback, continuity across rounds, user effort to express preferences, craft defects, handoff recoverability and time spent on mechanical work separately. A larger batch or a satisfied checklist is not automatically better. Keep observed failures and revise the owning method. Stop adding guidance when a clarified condition or fixed tool is the adequate repair.

For workbench acceptance, use the complete tasks in [collaboration and workbench design](collaboration/workbench.md). A coherent proposal supports design review; only implemented behavior can establish save/recovery and cross-view continuity. Static author walkthroughs are not user tests. Inspect design decisions separately from execution completion, so a successful tool run cannot silently close an unresolved design question.
