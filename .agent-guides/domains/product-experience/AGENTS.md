# Product-experience method

Use for uncertain product needs, mapping promises into experience, or assessing an existing complete path. This method adds progressive model and execution/report handoffs to [product design](../../scenarios/product-design.md) and [interaction modeling](../interaction-modeling/AGENTS.md). They retain requirement/scenario and binding/coverage authority. No second requirement catalog, operation registry, test engine or mandatory report platform is introduced.

| Current question | Apply | Useful result |
| --- | --- | --- |
| Data definitions or relationship-driven platform expression | [Semantic data basis](data-model.md), then consumer native contracts | Stable subjects from text to structured relations; reuse the consumer's existing page/scene/contract identities |
| Actor, role, need or use case remains vague | [Progressive models](models-and-workflows.md#progressive-models), with shared discovery/requirements | Source-backed distinctions, explicit assumptions, complete outcome slice and next uncertainty |
| Need must become pages and operations | [Design workflow](models-and-workflows.md#design-workflow), with experience/interface methods | Requirement → scenario → page/action/result bindings, including return and adverse branch |
| Candidate needs assessment | [Evaluation workflow](models-and-workflows.md#evaluation-workflow) | Bounded evidence, observation versus interpretation, finding owner and recheck |
| Prototype is operable and path meaning is stable | [Executable flow handoff](execution-and-reporting.md#flow-data-and-native-projection) | Versioned flow data and explicit existing-runner mapping |
| User needs to understand satisfaction | [Report projection and coverage](execution-and-reporting.md#report-projection) | Source/scenario/step/result links, real screenshots/trace and visible evidence gaps |

Before interface work, read [interface requirements](../../scenarios/interface-design.md) and the consuming project's standard. Reuse the current scenario and affected models for a narrow edit; these are entry choices, not sequential gates. Keep working results in the consumer's existing feature/Task. The [complete illustrative slice](examples/task-search/README.md) demonstrates the source, native binding and report handoff without claiming execution.

This method prescribes semantic handoffs rather than a universal file schema. Reuse the consumer's existing fields/IDs, runner and artifact store. If none exists, a small linked table or data file with native test code is enough. Unsupported actions remain explicit/manual; writing a generic parser or dashboard is a separate assignment.
