# Evaluate a candidate and retain the decision

Start with the decision and the evidence that could change it. Select the method: interviews explain remembered circumstances; actual task observation reveals use; expert review predicts risks; technical tests check contracts; controlled measurement can assess a defined outcome. Use existing evidence first. Without participants, report expert reasoning and a research plan; generated dialogue is not user research.

## Keep the claim attached to its context

Retain candidate/build, scenario and original criterion, state, fixture, environment, action, observation or quotation, relevant evidence, interpretation, owner and decision. [Observable feedback](../../scenarios/observable-feedback.md) owns capture details. Preserve actual words and actions separately from inferred causes or proposed implementation. Assistance changes the observation: record assisted completion rather than silently counting it as independent success.

A screenshot supports visible-state discussion; a recording adds time; actual interaction adds control and task behavior; an independent effect record adds the service result. Neither zero automated findings nor stable rendering establishes the whole experience. Compare the observed behavior to the original criterion before changing either.

## Review an existing product path

For tools, editors and workbenches whose risk lies in complete tasks, object/version/scope, fine control or interruption/return, select [tool experience review](scenarios/tool-experience-review.md). It combines task and cognitive walkthroughs with domain responsibilities and continuity. For source-completeness or action-to-call questions, compose [interaction modeling](../interaction-modeling/AGENTS.md); neither route creates a new scenario authority or universal quality score.

Choose an actor, intended result and actual channel. Follow the existing scenario source from entry through the result and a decisive interruption or return. Link the relevant criteria and current design; do not create another scenario catalog or turn adjacent future capabilities into prerequisites. Source inspection is an expert review, distinct from an executed path or independent user observation.

At each meaningful handover, ask what the next step needs, who supplies it, under which identity and conditions, and how the user can find and continue the work. Inspect both the mechanism and the entry to it. A completed export, a retained file and a discoverable download each need their own basis. If a location or session changes, check whether the old result remains identifiable and whether current access is still sufficient; retained history alone grants no new action authority.

Keep a short path table in the existing review or Task when it helps: user step, original criterion, supplying owner/entry, supporting observation and remaining uncertainty. Reuse prior evidence at its original version and scope. Review the important joins, not every artifact reachable from the feature.

### Decide what each finding calls for

Compare the finding with the chosen promise before selecting work. These are reasoning distinctions, not new entity types or mandatory status fields:

| Finding | Useful next action and owner |
| --- | --- |
| Evidence contradicts an existing chosen guarantee | Give the implementation owner a bounded defect with the original criterion and decisive check; preserve the guarantee unless a separate design decision changes it |
| A desired outcome extends or changes the current guarantee | Explain the product value and current/target difference in the owning Proposal; use [feature planning](../../scenarios/feature-planning.md#derive-proposals-from-the-product) to select priority and delivery |
| The intended guarantee is unclear or conflicting | Resolve the product/design question with concrete examples before declaring an implementation defect; keep an owned design dependency |
| The guarantee and mechanism exist, but the claimed environment or handover lacks evidence | Assign the missing bounded observation or integration check; do not invent a new capability merely to fill the evidence gap |
| A current explanation contradicts its authoritative source | Correct that explanation and affected navigation; preserve fixed historical captures and avoid a new capability Proposal |
| The selected guarantee is adequately supported, or the finding belongs to unrelated future scope | Retain the support or future direction with its limits; no new implementation work is required |

One observation may expose more than one issue. For example, an original export remains safely stored, yet returning users have no promised recovery entry. Preserve the storage result, distinguish the proposed discovery guarantee from missing usability evidence, and inspect the original target before adding a retry. A repeated operation in a new location can create a different effect even when the same identifier is supplied.

For the selected change, make the recommendation reviewable: before/after outcome, alternatives and tradeoffs, changed/retained promises, responsibility boundaries, compatibility and in-flight work, deciding checks, unresolved design dependencies and model return destinations. Keep these in the existing Proposal or bounded Task and owning designs. [Design management](../design-management/workflow.md#determine-the-affected-updates) owns the affected update set; [planning](../../scenarios/feature-planning.md#turn-an-outcome-into-a-delivery) owns execution decomposition. Do not create empty downstream work records for every candidate.

A design review can finish with a usable candidate and an assigned next decision or investigation. Record exactly what was established; it does not establish implementation, host support or user value. Reuse authorization already given for compatible refinements, and do not add a separate review gate.

## Compare candidates without conflating consultation and research

| Mode | Presentation | What the result means |
| --- | --- | --- |
| Independent response | Neutral labels, task before recommendation, record order and help | Research under stated presentation conditions |
| Decision consultation | Explain tradeoffs and a professional recommendation | User direction or choice, not blind preference evidence |
| Joint ideation | Invite alternatives, combinations and demonstrations | New design clues, not proof one existing candidate won |

For a meaningful comparison, hold task, object, data, critical success/failure semantics, fidelity and environment steady. If complete packages differ in several dimensions, draw conclusions about the packages, not one color or motion parameter. Do not create a deliberately weak alternative. Allow “neither” and unresolved choice.

Use sequential task attempts before side-by-side preference discussion when behavior matters. Within-person comparisons permit detailed reasons but introduce learning/fatigue; vary order and preserve first-attempt results. Between-person comparison can reduce learning but needs comparable recruitment and assignment. Small preference counts do not become a statistical A/B result. Static parallel candidates suit visual expression, not interaction efficiency.

A useful round is: declare decision and outcome categories → freeze material → give a neutral goal → observe attempts and assistance → ask what the person thinks happened → discuss comparison and feelings → decide and assign a recheck. “Keep this result so you can find it later” observes discovery; “click Save at bottom right” teaches the answer. Separate a deliberate prompted-comprehension test from natural task discovery.

## Preserve feelings and make explanations testable

“Sudden”, “slow” and “reassuring” are meaningful reports, not ready-made specifications. Retain the phrase and exact moment, action and environment. Distinguish self-report from your interpretation. Propose mechanisms such as lost continuity, delayed input acknowledgement or unclear outcome; inspect evidence before changing duration or layout. Ask what happens and what caused that impression without preloading your preferred diagnosis.

Judge constraints and serious failures first, then task correctness and comprehension, then preference and maintenance tradeoffs among viable choices. Faster completion is not automatically better if error detection declines. A blocking accessibility failure is not overruled by aesthetic votes.

## Close the feedback loop

Route a finding to its actual owner: goal/requirements, navigation/content, behavior/authority, shared presentation rule or local treatment. Record adoption, revision, deferral or rejection with reasons. Retain original evidence and link a new check under the changed version to the original finding.

For outcome metrics, state population, numerator/denominator, window, baseline and relevant guardrails. Compare like conditions, include missing/failed observations and distinguish correlation from a causal claim. A one-session improvement cannot establish lasting adoption. Stop when the decision has adequate bounded evidence and unresolved uncertainty has a concrete next owner or investigation; collecting more screenshots is not itself progress.

Further sources: [GOV.UK moderated testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing), [NN/g method selection](https://www.nngroup.com/articles/which-ux-research-methods/). This method preserves observed scope; it does not certify research reliability from completed fields.
