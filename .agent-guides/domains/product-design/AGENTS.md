# Product design methods

Before designing, implementing or reviewing a user interface, read [product and interface design requirements](../../scenarios/interface-design.md). These required constraints apply across product, page, management, tool and mobile design; select professional depth below without postponing this read.

Use when a product decision needs deeper professional work. The root [product-design scenario](../../scenarios/product-design.md) owns the connected method and single scenario source; [feature planning](../../scenarios/feature-planning.md) owns selected outcomes and delivery ownership. Enter at the unresolved question. These methods do not require twelve documents, a prescribed stack or a new research campaign.

| Professional concern | Read when | Method and usable result |
| --- | --- | --- |
| Product discovery | Actor, need, obstacle or value is uncertain | [Discovery](discovery.md): evidence-backed problem, alternative explanations and next decisive question |
| Requirements and feature behavior | Continuing feature scope, need/scenario relationships, interaction promises or acceptance are unclear | [Requirements](requirements.md), including [feature identity](requirements.md#identify-the-continuing-feature) and [interaction promises](requirements.md#define-feature-and-interaction-promises): complete outcomes, conditions, results and coverage |
| Experience architecture | People must find, understand or return to a task | [Web experience](../webdevelopment/experience-design.md): objects, navigation, surfaces, content and recovery; [navigation contracts](../webdevelopment/navigation-and-recovery.md) for surface/address/return decisions; [tool interfaces](../webdevelopment/tool-interfaces.md) for analysis/workbench products |
| Prototyping | A decision needs an operable candidate | [Prototypes](prototyping.md): appropriate fidelity, representative data, behavior and explicit simulation limits |
| Feedback and validation | Review an existing product path, choose research/evaluation or compare treatments | [Evaluation](evaluation.md), including [path review and finding disposition](evaluation.md#review-an-existing-product-path): observations, current/target differences, owned decisions and rechecks with bounded claims |
| Tool experience and precision | Review a workbench/editor across tasks, object scope, discovery, fine controls, interruption or return | [Tool experience review](scenarios/tool-experience-review.md): complete task and responsibility, cognition, continuity, precision and actionable findings; keep expert prediction distinct from observed use |
| Progressive experience models and execution handoff | Actors/needs evolve or scenario promises need native-test/report handoffs | [Product experience](../product-experience/AGENTS.md): refine the same semantic subjects, preserve original criteria and bind supported steps to existing runners |
| Interaction coverage and bindings | Connect the canonical scenario, native operations and UI actions or challenge a completeness claim | [Interaction modeling](../interaction-modeling/AGENTS.md): independent source inventories, binding/result/state paths and scoped evidence |
| System architecture | Establish capability, fact or host boundaries | [Engineering composition](../../scenarios/engineering-design.md#domain-module-and-product-composition); [collaborative modeling](../../scenarios/collaborative-modeling.md) for unresolved semantics and [data/state modeling](../../scenarios/data-state-modeling.md) for domain/lifecycle rules. Use [bounded modeling checks](../modeling/AGENTS.md) only for a selected check or projection |
| Interface design | Compose pages, screens and components | [Interface structure](../webdevelopment/interface-structure.md), [component contracts](../webdevelopment/component-design.md), [interaction](../webdevelopment/interaction-and-state.md) |
| Design systems | Establish shared or scoped expression | [Design system](../webdevelopment/design-system.md): tokens, rules, themes and canonical components |
| Motion | Explain change, timing or interaction | [Motion](../webdevelopment/motion.md): triggers, continuity, interruption, reduced motion and actual temporal evidence |
| Assets and content | Meaning depends on copy, imagery or media | [Content and assets](../webdevelopment/content-and-assets.md), [assets](../webdevelopment/assets.md): content model, source identity, production brief and in-context acceptance |
| Engineering delivery | Quality, integration or operation affects a promise | [Quality and delivery](quality-and-delivery.md), [release and recovery](../../scenarios/release-and-recovery.md): actual boundary evidence and recoverable delivery |
| Toolchain and knowledge | Select an execution or reusable mechanism | [Technology selection](../../scenarios/engineering-design.md#technology-selection-design), [skill research](../../scenarios/skill-research.md), [registries](../webdevelopment/registry.md), [API/SDKs](../../scenarios/api-contracts-and-sdks.md): supported tools, resources and original contract ownership |

Apply matching methods together and exchange results by reference. Requirements say what must be achieved; prototypes test selected assumptions; architecture says who can uphold a promise; evidence supports or refutes it. A successful tool invocation cannot supply missing product meaning. Keep designs, research, scenarios and actual runs with the responsible consumer. Normal work needs these methods and the installed tool's usage, not the author's research controller.

Use the root method's [complete feature design questions](../../scenarios/product-design.md#organize-a-complete-feature-design) to choose what needs explanation. Use [design management](../design-management/workflow.md#maintain-a-features-current-design) to maintain those sources across changes. These routes reuse professional facts rather than creating a parallel feature specification.

For a management console or workbench spanning multiple subjects and actions, use [management product design](../management-product-design/AGENTS.md) to connect these methods into object navigation, page hierarchy and complete work paths. It does not replace the professional owners above or require a full redesign for a bounded fix.
