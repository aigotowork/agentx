# Give content and visual assets a product contract

Use when text, imagery, diagrams or media carry task meaning. The existing [assets method](assets.md) owns briefs, sourcing, integration and acceptance; [design system](design-system.md) owns shared expression. This guide deepens content structure and candidate production without choosing a generation vendor.

## Model content before filling placeholders

Identify the user question, content object and its owner, required fields/units, source, update/localization lifecycle and permitted transformations. Separate authoritative facts, derived display, editorial explanation and example data. A label, notification and long explanation can reference one fact without becoming three independent authorities.

Use terms from the user's task. Write actions by their effect, status by the known result and errors with a supported recovery. “Saved” requires the actual save result; “Nothing here” must not conceal denied or failed reading. Preserve important consequences beside the action. Long, missing, plural, translated and mixed-script content can change layout and accessibility, so use representative cases early.

For instructional or persuasive content, state intended understanding and next action, evidence for factual claims and any remaining uncertainty. A style preference cannot justify inventing statistics, testimonials or user research. Check hierarchy, scanability, tone and comprehension in the actual task; copy completeness alone does not establish usability.

## Choose the resource form

Use existing code-native icons, SVG, CSS or canvas when those fit the asset's role and need precise adaptation. Use a bitmap when photography, illustration, texture or generated imagery serves the task. A semantic diagram preserves relation meaning and labels; it should not become an unverifiable image when readers need inspectable data or accessible text.

For each resource, define audience/task, role, semantic content, placement, dimensions/aspect ratio, responsive crop, theme/background, transparency, motion and accessibility alternative. Record source/license, editable original, transformation and consuming component. Keep source assets and optimized derivatives connected; file location alone does not prove provenance or permitted redistribution.

## Prepare a visual batch without claiming it was generated

Translate ordinary intent into a small number of distinct directions with reasons tied to structure, content and tone. Keep product facts and scene steady for comparison. A UI recipe, an illustration medium and an output format are separate choices: a warm editorial interface does not automatically require every asset to use the same texture.

If an installed preparation Skill is selected, read its native entry and shipped catalog/contract. Supply an explicit brief and a new consumer output directory; do not edit the installed catalogs or use the author's historical run path. A preparation tool emits prompts, formats, dependencies and source references. It does not submit image requests, prove licensing, produce actual images or create an executable design system.

Make render content explicit for each output: what the image visibly contains, hierarchy, labels or text constraints, state, crop and relevant reference. Keep review intent, behavior and source notes outside visible image text unless deliberately requested. Do not ask a generator to reconstruct a missing scene from an internal brief identifier.

Produce a representative direction board and asset sample before dependent screens/states. Select a coherent reference set for each family, then generate or edit through the actually available capability under current task authority. Preserve request/reference identity, raw result and revision, and distinguish failed/missing outputs. Read the actual image as part of UI design or its fit-to-intent review, explaining its visible content, hierarchy, placement and relation to the consuming task; asset production alone is not a reason for routine image inspection. A catalog entry without a sample is knowledge to try, not a proven style library.

## Hand off and judge in context

Convert accepted visual relationships into explicit layout, type, spacing, color and component rules. Extract actual standalone assets where needed and maintain theme/variant identity. An image of a screen is a reference, not an implemented accessible interface. Keep interaction/state contracts with the component, including pending/error/disabled/focus states absent from the image.

Review an integrated result in the target component and responsive/theme contexts: crop, contrast, text legibility, resolution, download/decode cost, provenance and task fit. Retain editable originals and purposeful variants rather than accumulating indistinguishable revisions. Compare candidates through [evaluation](../product-design/evaluation.md); do not label a generated batch as accepted because preparation or download succeeded.
